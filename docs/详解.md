# Agent 运行时详解：一步一步做，每步说为什么

这份是手把手的详解，每一步都是：做什么、为什么、怎么验证、常见错误。代码骨架给到函数签名和关键行，空的地方你自己填，填完跑，对照"验证"里写的预期输出。

**场景**。全文围绕一个真实业务：一个知识付费平台，创作者写小册子，读者买来读，平台给每本书配 AI 导读、复习题和能答问题的助教。业务后端是 Go，负责租户、身份、订单、额度；AI 服务是 Python，只负责生成，由 Go 内部调用。这份教程写的就是那个 Python 服务的运行时层。第 7 章起会反复出现"创作者""读者""Go 主服务""租户"，指的都是这个场景。

**线上版**。文中说"线上版"，指作者在生产环境跑着的那份实现。它踩过的坑会随章节引用，比如失败分支 token 记成 0、回调失败被记成 Agent 失败。你看不到它的代码，不影响学习；第 10 章末尾有一份它和教程版本的对照结论。

**前置**。会一门编程语言，Python 不熟也行，用到的语法会随手讲。需要一个 OpenAI 兼容接口的模型 API（文中用 DeepSeek），一台装了 uv 的机器。

## 第 0 章 搭建项目

### 0.1 为什么用 uv

Python 项目要解决三件事：用哪个 Python 版本、装了哪些包、这些包装在哪里不污染别的项目。传统做法是 pyenv 管版本、venv 建隔离环境、pip 装包、requirements.txt 记清单，四个工具。uv 一个顶四个，而且快。

uv 的三个文件：

| 文件 | 作用 | 要不要提交到 git |
|---|---|---|
| pyproject.toml | 项目名、Python 版本要求、依赖清单。你手写或 uv add 自动改 | 要 |
| uv.lock | 每个依赖的精确版本和哈希，保证换台机器装出来一模一样 | 要 |
| .venv/ | 真正装包的目录，几百 MB | 不要，已在 .gitignore |

### 0.2 建项目

```bash
mkdir agent-runtime && cd agent-runtime
uv init --python 3.12
uv add httpx python-dotenv
printf '.env\n.venv\n__pycache__/\nruns.db\n' > .gitignore
uv --version            # uv 0.11 左右
uv run python --version # Python 3.12.x
cat pyproject.toml      # dependencies 里有 httpx 和 python-dotenv
```

`uv init` 会生成一个示例 main.py，删掉，第 7 章会写自己的。

`uv run python xxx.py` 的意思是：用 .venv 里的 Python 跑这个文件。不用 `source .venv/bin/activate`，uv run 每次自动找。为什么不用系统的 python3：系统 Python 没装 httpx，而且不同项目的包会互相打架。

### 0.3 .env 是什么

.env 文件里是 `KEY=VALUE` 一行一个，放密钥和地址。为什么单独一个文件：

- 密钥不能进代码，代码会进 git，git 会推到远端，远端谁都可能看到。.env 在 .gitignore 里，永远不会被提交。
- 换厂商只改 .env，代码不动。DeepSeek 换成通义，改三行配置。

新建 .env，第 1 章只需要前三个变量，EMBEDDING 那组到用时再加：

| 变量 | 含义 | 第几章用 |
|---|---|---|
| LLM_BASE_URL | 厂商接口地址，形如 https://api.xxx.com/v1 | 1 |
| LLM_API_KEY | 密钥 | 1 |
| LLM_MODEL | 模型名，形如 deepseek-chat | 1 |
| EMBEDDING_* | 向量模型那一套 | 后续五个 Agent 教程第 2 章，现在不用 |

### 0.4 建一个 git 仓库

建 git 仓库，以后每章做完提交一次，这样搞坏了能回退，也能看自己每章写了什么。

```bash
git init
git add .
git commit -m "init: 教程与项目骨架"
```

提交前 `git status` 看一眼，.env 和 .venv 不应该出现在待提交列表里。出现了说明 .gitignore 没生效，停下来查。

### 0.5 验收

- `uv run python -c "import httpx, dotenv; print('ok')"` 打印 ok。
- `git log --oneline` 有一条提交。
- `git status` 干净。

## 第 1 章 模型接口就是 HTTP

### 这一章解决什么问题

你以后会用 LangChain、openai 包，它们把调模型包成一行 `model.invoke("你好")`。包得太好，出了问题你不知道里面发生了什么：为什么 400？token 怎么算的？流式为什么卡？这一章不用任何壳，用 httpx 直接发 HTTP，看清楚那一行里面到底是什么。看清楚一次，以后用壳就踏实了。

### 先看懂接口长什么样

所有厂商的聊天接口都抄 OpenAI 的格式，叫 chat completions。一次调用就是一个 HTTP POST：

```
POST {LLM_BASE_URL}/chat/completions
Authorization: Bearer {LLM_API_KEY}
Content-Type: application/json

{
  "model": "deepseek-chat",
  "messages": [
    {"role": "system", "content": "你是一个助教"},
    {"role": "user", "content": "用一句话介绍 RAG"}
  ]
}
```

返回：

```json
{
  "choices": [{
    "message": {"role": "assistant", "content": "RAG 是……"},
    "finish_reason": "stop"
  }],
  "usage": {"prompt_tokens": 23, "completion_tokens": 41, "total_tokens": 64}
}
```

三个要认的字段：

- `choices[0].message.content`：回答正文。为什么是 choices 列表：接口允许一次要 n 个候选回答，默认 1 个，所以永远取 [0]。
- `choices[0].finish_reason`：为什么停。`stop` 是正常说完，`length` 是被 max_tokens 截断了，`tool_calls` 是它想调工具。第 6 章结构化输出时 `length` 会导致 JSON 不完整，现在先记住有这个值。
- `usage`：token 用量。算钱全靠它，第 4 章记账要存。

### 1.1 读配置

**做什么**：新建 `l1_hello.py`，读 .env 的三个变量并打印，密钥只打印前 6 位。

**骨架**：

```python
import os
from dotenv import load_dotenv

load_dotenv()
BASE_URL = os.environ["LLM_BASE_URL"]
API_KEY = ...
MODEL = ...

print(BASE_URL, MODEL, API_KEY[:6])
```

**为什么**：

- `load_dotenv()` 做的事：打开当前目录的 .env，逐行解析 `KEY=VALUE`，塞进 `os.environ`。它不会覆盖已经存在的环境变量。
- 用 `os.environ["X"]` 不用 `os.environ.get("X")`。前者缺了立刻抛 KeyError 并告诉你缺哪个；后者返回 None，带着 None 跑到发请求那一步才炸，报错是 "NoneType has no attribute"，你得倒回来查。配置缺失要在最早的地方炸。
- 变量名全大写放模块顶层，是 Python 的约定：这是常量，整个文件都用。

**验证**：`uv run python l1_hello.py` 打印一行，三段都不是空。

**常见错误**：

- 打印 KeyError：.env 不在当前目录，或者变量名拼错。`cat .env` 对一下。
- ModuleNotFoundError: dotenv：用了系统 python 而不是 uv run。

### 1.2 发第一个请求

**做什么**：问"用一句话介绍 RAG"。先把整个返回体打印出来看结构，再分别打印回答、finish_reason、输入 token、输出 token。

**骨架**：

```python
import httpx
import json

client = httpx.Client(base_url=BASE_URL, timeout=60, trust_env=False)
HEADERS = {"Authorization": f"Bearer {API_KEY}"}

def chat(messages: list[dict]) -> dict:
    resp = client.post("/chat/completions", headers=HEADERS,
                       json={"model": MODEL, "messages": messages})
    resp.raise_for_status()
    return resp.json()

data = chat([{"role": "user", "content": "用一句话介绍 RAG"}])
print(json.dumps(data, ensure_ascii=False, indent=2))
# 下面四行你自己写：回答、finish_reason、prompt_tokens、completion_tokens

# print(f"回答：{data['choices'][0]['message']['content']}")
# print(f"finish_reason：{data['choices'][0]['finish_reason']}")
# print(f"prompt_tokens：{data['usage']['prompt_tokens']}")
# print(f"completion_tokens：{data['usage']['completion_tokens']}")

# 回答：RAG（检索增强生成）是一种让大语言模型在生成回答前先从外部知识库检索相关信息、再基于检索内容生成答案的技术，从而提升回答的准确性和时效性。
# finish_reason：stop
# prompt_tokens：9
# completion_tokens：40
```

**为什么**：

- 用 `httpx.Client` 而不是 `httpx.post`：Client 会复用 TCP 连接。一个 Agent 一轮要发十几次请求，每次重新握手要多几百毫秒。现在感觉不到，第 3 章循环起来就有感觉了。
- `base_url` 设在 Client 上，之后只写路径 `/chat/completions`。换厂商改 .env 就行，代码里没有任何厂商地址。
- `timeout=60`：httpx 默认 5 秒，模型回答长一点就超时。60 秒是后台任务的值，第 8 章问答实时场景会改成 20 秒。
- `trust_env=False`：httpx 默认读系统的 HTTP_PROXY 环境变量走代理，开了代理软件的电脑经常因此连不上。关掉它，让 httpx 直连。
- `raise_for_status()`：HTTP 状态不是 2xx 就抛异常。不加这行，400 的时候 `resp.json()` 返回的是错误信息，你会在下一行取 choices 时拿到 KeyError，报错位置是错的。错误要在发生的地方抛。
- 先 `json.dumps` 整个打出来：你要亲眼看到 choices、message、usage 的嵌套，而不是背我上面写的。`ensure_ascii=False` 让中文直接显示而不是 \uXXXX。
- 把发请求包成 `chat()` 函数：后面 1.3 和 1.4 还要调好几次。一个函数只做一件事：发请求、返回解析后的 dict，不打印。打印是调用方的事。

**验证**：四行分别打印出来。记下 prompt_tokens 是多少，1.3 要对比。

**常见错误**：

- `httpx.HTTPStatusError: 401`：密钥错。嗯嗯。
- `404`：BASE_URL 多了或少了 `/v1`。打印一下 `client.base_url` 看拼出来的完整地址。
- `ConnectError`：代理问题，确认 trust_env=False 写了。
- 中文乱码：加 ensure_ascii=False。

### 1.3 让模型输出 JSON，看它听不听话

**做什么**：加一条 system 消息："你只能输出 JSON，格式 {"answer": string, "confidence": number}"。用 `json.loads` 解析回答，解析失败接住 `json.JSONDecodeError` 打印原文。跑 5 次，记录成功几次。

**骨架**：

```python
SYSTEM = '你只能输出 JSON，格式 {"answer": string, "confidence": number}，不要输出其他任何文字。'

ok = 0
for i in range(5):
    data = chat([
        {"role": "system", "content": SYSTEM},
        {"role": "user", "content": "用一句话介绍 RAG"},
    ])
    text = data["choices"][0]["message"]["content"]
    try:
        obj = json.loads(text)
        ...   # 成功：ok 加一，打印 obj["answer"]
    except json.JSONDecodeError:
        ...   # 失败：打印第几次、原文
print(f"{ok}/5 成功")
```

**为什么**：

- system 消息放第一条，是接口的约定。它是"工作说明"，用户消息是"这次的任务"。线上版的 prompts/ 目录存的全是 system 消息。
- `json.loads` 失败要接 `JSONDecodeError` 而不是裸 `except:`。裸 except 会把 KeyboardInterrupt 也吞了，Ctrl+C 停不下来。只接你预期的那一种异常。
- 失败时打印原文：你会看到模型常见的几种不听话：外面包一层 ```json 代码块、前面加一句"好的，以下是"、confidence 写成字符串。这些是第 6 章结构化输出要处理的全部情况，现在先见过。
- 跑 5 次是因为模型输出有随机性，一次成功说明不了什么。

**验证**：打印 `n/5 成功`。多半不是 5/5。把失败的原文留着，看它们属于上面哪一种。

**这一步的结论**：靠提示词让模型输出 JSON 不可靠，所以第 6 章要用厂商的 function calling 强制格式，并且解析失败要打回重试。你现在亲眼看到了"为什么"。

### 1.4 流式

**做什么**：请求体加 `"stream": True`，逐行读返回，边收边打印，记录首字延迟和总耗时。

**骨架**：

```python
import time

def chat_stream(messages: list[dict]):
    t0 = time.monotonic()
    first = None
    with client.stream("POST", "/chat/completions", headers=HEADERS,
                       json={"model": MODEL, "messages": messages, "stream": True}) as resp:
        resp.raise_for_status()
        for line in resp.iter_lines():
            if not line.startswith("data: "):
                continue
            payload = line[len("data: "):]
            if payload == "[DONE]":
                break
            chunk = json.loads(payload)
            delta = chunk["choices"][0]["delta"].get("content")
            if not delta:
                continue
            if first is None:
                first = time.monotonic() - t0
            print(delta, end="", flush=True)
            pieces.append(delta)          # 攒起来，1.5 要用
    print()
    print(f"首字 {first:.2f}s，总耗时 {time.monotonic() - t0:.2f}s")
    return "".join(pieces)
```

`pieces = []` 放在 `first = None` 旁边，你自己加。

有几处故意写全了，因为流式协议的细节不是能推出来的，是约定。你要做的是读懂每一行，然后合上默写。

**为什么**：

- 流式返回不是一个 JSON，是 SSE 格式：一行一行的 `data: {...}`，最后一行 `data: [DONE]`。中间有空行，所以要跳过不以 `data: ` 开头的行。
- `client.stream(...)` 配 `with`：流式连接要一直开着收数据，with 结束时自动关。不用 with 容易泄露连接。
- 正文在 `delta.content` 而不是 `message.content`：每一片只有增量，叫 delta。第一片通常只有 role 没有 content，所以要 `.get` 并跳过空的。
- `print(..., end="", flush=True)`：end="" 不换行，字才能连起来。flush=True 强制立刻写到终端，不然 Python 会攒到缓冲区满或换行才输出，你会看到一大段一起蹦出来，流式就白做了。
- `time.monotonic()` 而不是 `time.time()`：monotonic 只会往前走，系统校时也不会跳。测耗时一律用它。
- 首字延迟才是流式的指标。总耗时流式和非流式差不多，流式的价值是读者 0.5 秒就看到第一个字而不是等 8 秒。

**验证**：字一个个蹦出来，最后一行打印两个时间。首字应该明显小于总耗时。

**常见错误**：

- 一整段一起出现：没加 flush=True。
- `KeyError: 'delta'`：某些厂商最后一片带 usage 没有 choices，加一个 `if not chunk["choices"]: continue`。
- 不停在 [DONE]：有的厂商 `data:` 后面没空格，用 `line.removeprefix("data:").strip()` 更稳。

### 1.5 流式加 JSON 校验

**做什么**：用 1.3 的 system 消息走流式，流完之后对 `chat_stream` 返回的完整文本做 `json.loads`，失败接住打印原文。跑 5 次记成功几次，和 1.3 的非流式对比。

**骨架**：

```python
ok = 0
for i in range(5):
    text = chat_stream([
        {"role": "system", "content": SYSTEM},
        {"role": "user", "content": "用一句话介绍 RAG"},
    ])
    try:
        ...   # json.loads(text)，成功 ok 加一
    except json.JSONDecodeError:
        ...   # 打印第几次、原文
print(f"{ok}/5 成功")
```

**为什么**：

- 不能对每一片 delta 做 json.loads。一片可能只是 `{"ans`，永远解析不了。JSON 只有收完整才能判断合不合法，所以 chat_stream 要把片攒起来、流完再返回整段。这是 1.4 加 `pieces` 的原因。
- 这里有一个流式和结构化输出天生的矛盾：流式的价值是边收边用，JSON 的校验要等收完。两者不能兼得。线上版的解法是分开：问答这种给读者看的用流式、不要 JSON；出题这种要 JSON 的不用流式。第 8 章问答只有一个例外，首行的档位标签要在流的开头判断，办法是攒到第一个换行再判，叫"攒头判断"。你现在做的就是攒头判断的全量版：攒到结尾再判。
- 解析在 with 外面做，不在流的循环里。循环里只做一件事：收片。判断留给调用方。职责分开，第 8 章接 SSE 路由时 chat_stream 不用改。

**验证**：打印 `n/5 成功`。成功率应该和 1.3 差不多，因为模型是同一个，流式只改了传输方式不改内容。如果差很多，看原文，多半是流式末尾少收了一片。

**这一步的结论**：流式不帮你解决 JSON 不可靠的问题，只是把解析推迟到最后。该校验、该重试的，第 6 章一样要做。

1. 模型怎么记住上一轮对话？

## 第 2 章 工具调用协议

### 这一章解决什么问题

第 1 章模型只会"说"。这一章让它会"要"：你告诉它有哪些函数可用，它需要时不回答，改成返回"请帮我调某个函数，参数是这些"。你执行，把结果塞回去，它接着想。这就是 Agent 的全部秘密，第 3 章只是把这个过程套进循环。

先把一个误解掐掉：**模型不执行任何东西**。它返回的只是一段结构化的"我想调什么"，执行是你的代码干的。所以模型越权不了，你不给的函数它调不到；你给的函数怎么防参数乱传，是你的事。

### 协议长什么样

请求里多一个 `tools` 字段，每个工具是一段 JSON Schema 描述：

```python
tools = [{
    "type": "function",
    "function": {
        "name": "add",
        "description": "两个整数相加",
        "parameters": {
            "type": "object",
            "properties": {"a": {"type": "integer"}, "b": {"type": "integer"}},
            "required": ["a", "b"],
        },
    },
}]
```

模型决定要工具时，返回和第 1 章不一样：

```json
{
  "choices": [{
    "finish_reason": "tool_calls",
    "message": {
      "role": "assistant",
      "content": null,
      "tool_calls": [{
        "id": "call_abc123",
        "type": "function",
        "function": {"name": "add", "arguments": "{\"a\": 17, \"b\": 25}"}
      }]
    }
  }]
}
```

三处要盯住：`finish_reason` 变成 `tool_calls`；`content` 是 null；`arguments` 是**字符串**不是字典，要 `json.loads`。

你执行完，往 messages 追加两样东西，再发一次：

```python
messages.append(msg)                                   # 规则 1：模型那条带 tool_calls 的消息原样放回
messages.append({"role": "tool", "tool_call_id": call["id"], "content": "42"})   # 规则 2：每个 call 一条
```

两条硬规则，违反都是厂商报 400：模型的 assistant 消息必须原样放回；每一个 tool_call 都要有一条对应的 tool 消息，少一个都不行。2.4 会让你故意违反一次，看报错长什么样。

### 2.0 先整理第 1 章的代码

第 2 章要用 `chat()`。直接 `from l1_hello import chat` 不行，因为 l1_hello.py 顶层有 print 和请求，一 import 就全跑一遍。这是 Python 的规则：import 一个文件就是从头到尾执行它。

两个办法，选一个：

- 简单：新建 `l2_tools.py`，把读配置、建 client、`chat()` 那十来行复制过去。重复一次没关系，第 3 章会抽成共享模块。
- 规范：把 l1_hello.py 里的每一步包成函数 `step1()`、`step2()`……，最底下写：

```python
if __name__ == "__main__":
    step4()
```

`__name__` 这个变量，直接运行文件时等于 `"__main__"`，被 import 时等于文件名。所以这个 if 的意思是"只有直接运行我才跑下面的"。有了它，l2_tools.py 就能安全地 `from l1_hello import chat, client, HEADERS, MODEL`。

推荐第二种，顺便把注释掉的代码恢复成函数，以后每一步都能单独跑。

### 2.1 写两个工具和它们的 schema

**做什么**：在 `l2_tools.py` 里写两个普通函数，再手写它们的 JSON Schema 放进 `TOOLS_SCHEMA` 列表，用一个字典 `TOOLS` 把名字映射到函数。

**骨架**：

```python
from datetime import datetime

def get_time() -> str:
    """返回当前时间，格式 2026-10-22 21:30:05"""
    return ...

def add(a: int, b: int) -> int:
    return a + b

TOOLS = {"get_time": get_time, "add": add}

TOOLS_SCHEMA = [
    {"type": "function", "function": {
        "name": "get_time",
        "description": "...",
        "parameters": {"type": "object", "properties": {}, "required": []},
    }},
    {"type": "function", "function": {
        "name": "add",
        "description": "...",
        "parameters": ...,     # 照上面协议那段写
    }},
]
```

**为什么**：

- 函数本身就是普通 Python 函数，不需要任何装饰器、不需要继承什么类。LangChain 的 `@tool` 只是帮你从函数签名自动生成下面那段 schema，第 10 章你会看到它省了什么。现在手写一遍，才知道它生成的是什么。
- `description` 是写给模型看的，决定它什么时候会想到用这个工具。写"两个整数相加"比写"add"有用得多。模型只看描述，不看你的函数体。
- `TOOLS` 字典是"名字到函数"的映射。模型返回的是名字字符串，你要靠它找到函数。这个字典第 3 章会原样进 run_loop。
- 没有参数的工具 `properties` 是空字典，`required` 是空列表，不能省略 parameters 字段，有的厂商会 400。

**验证**：

```bash
uv run python -c "from l2_tools import add, get_time; print(add(1, 2), get_time())"
```

打印 `3` 和一个时间。schema 还没验证，下一步发出去才知道对不对。

### 2.2 发一次带 tools 的请求，看模型怎么要

**做什么**：给 `chat()` 加一个可选参数 `tools`，有就塞进请求体。问"现在几点，另外 17 加 25 等于多少"，打印 `finish_reason` 和 `tool_calls`。

**骨架**：

```python
def chat(messages: list[dict], tools: list[dict] | None = None) -> dict:
    body = {"model": MODEL, "messages": messages}
    if tools:
        body["tools"] = tools
    resp = client.post("/chat/completions", headers=HEADERS, json=body)
    resp.raise_for_status()
    return resp.json()

messages = [{"role": "user", "content": "现在几点，另外 17 加 25 等于多少"}]
data = chat(messages, tools=TOOLS_SCHEMA)
msg = data["choices"][0]["message"]
print(data["choices"][0]["finish_reason"])
print(json.dumps(msg.get("tool_calls"), ensure_ascii=False, indent=2))
```

**为什么**：

- `tools` 做成可选参数而不是永远传，因为第 1 章那种纯聊天不需要工具，传了空列表有的厂商报错。
- 问题故意包含两件事，是要你观察：模型一次返回两个 tool_calls，还是先要一个、拿到结果再要另一个。两种都合法，不同模型不同习惯。DeepSeek 多半一次要两个。这决定第 3 章的循环要能处理"一轮多个调用"。
- 打印 `msg.get("tool_calls")` 用 get，因为模型也可能不要工具直接回答，那时没有这个字段。

**验证**：finish_reason 是 `tool_calls`，tool_calls 列表里一到两个元素。把 `arguments` 的值看清楚：它外面有引号，是字符串。

**常见错误**：

- 400 且错误里提到 tools：schema 写错了，多半是 parameters 里缺 type: object，或者 required 里的名字和 properties 对不上。把厂商返回的错误原文打出来：`except httpx.HTTPStatusError as e: print(e.response.text)`。
- 模型没要工具直接回答了：description 写得太含糊，或者问题没说清。改 description 再试。

### 2.3 执行、回传、再发，直到 stop

**做什么**：执行 tool_calls 里的每一个，按协议回传，再发一次。因为模型可能分两轮要，用一个最多 5 次的 for 循环兜着，`finish_reason` 变成 `stop` 就打印最终回答并跳出。

**骨架**：

```python
messages = [{"role": "user", "content": "现在几点，另外 17 加 25 等于多少"}]

for round_no in range(5):
    data = chat(messages, tools=TOOLS_SCHEMA)
    choice = data["choices"][0]
    msg = choice["message"]
    messages.append(msg)                                 # 规则 1，不管要不要工具都放回

    if choice["finish_reason"] != "tool_calls":
        print("最终回答：", msg["content"])
        break

    for call in msg["tool_calls"]:
        name = call["function"]["name"]
        args = json.loads(call["function"]["arguments"])
        result = TOOLS[name](**args)
        print(f"  调用 {name}({args}) -> {result}")
        messages.append({                                # 规则 2
            "role": "tool",
            "tool_call_id": call["id"],
            "content": str(result),
        })
```

**为什么**：

- `messages.append(msg)` 放在判断之前：不管这轮模型是要工具还是直接回答，它说的话都要进历史。第 1 章说过，模型没有记忆，历史是你维护的。
- `json.loads(arguments)` 必须做。它是字符串，`TOOLS[name](**args)` 的 `**` 要的是字典。
- `**args` 的意思是把字典拆成关键字参数：`{"a": 17, "b": 25}` 变成 `add(a=17, b=25)`。所以 schema 里的参数名必须和函数的形参名一致，不然 TypeError。
- `content` 要 `str()`：协议规定 tool 消息的 content 是字符串，`add` 返回的是 int，直接塞会 400。
- 用有上限的 for 而不是 while True：模型如果一直要工具，while True 会无限烧钱。5 次是临时值，第 3 章 run_loop 会把它做成参数 max_steps。
- 这个 for 循环已经是 Agent 循环的雏形。第 3 章做的只是把它包成函数、加出口判断、加工具出错处理。

**验证**：打印一到两行"调用 xxx -> 结果"，然后打印最终回答，回答里应该同时有时间和 42。

**常见错误**：

- `TypeError: add() got an unexpected keyword argument`：schema 参数名和函数形参名不一致。
- 400 提到 tool_call_id：规则 2 没满足，多半是 for 里某个 call 漏回传了，或者 msg 没放回去。
- 一直不 stop：模型拿到结果又要了一次同样的工具。打印每轮的 messages 长度看，多半是 tool 消息的 content 没让它满意，比如返回了空字符串。

### 2.4 故意弄坏两次，记下报错原文

**做什么**：两个实验，每个做完恢复代码再做下一个。错误原文记进 README 笔记。

**实验一**：把 `add` 的 schema 里 `b` 从 properties 和 required 都删掉，再问同样的问题。看模型怎么调 add：它会只传 a？会编一个 b？还是放弃用工具自己算？

**实验二**：恢复 schema。在 2.3 的内层 for 里加一句，让第二个 call 不回传（比如 `if call is msg["tool_calls"][-1]: continue` 放在 append 前面，并打印一下确认跳过了）。看厂商返回什么错，用 `except httpx.HTTPStatusError as e: print(e.response.text)` 把原文抓出来。

**为什么**：

- 实验一让你看到 schema 是模型行为的唯一依据。schema 缺了参数，模型要么编要么放弃，两种都是生产事故。线上版的工具 schema 里 `booklet_id` 是必填，就是防它编一个。
- 实验二是让你亲眼见一次那个 400。线上版出题时 7 章因为这个 400 过，教训写在 quiz/agent.py 的注释里。见过一次，第 3 章工具出错时你就知道为什么必须回一条错误消息而不是跳过。

**验证**：README 笔记里有两段报错原文，各一句你对它的理解。

**实验一观察记录（2026-10-22 实测，DeepSeek）**：

1. 删掉 schema 里的 b 后，模型调用 `add({'a': 17})`，只传 a，没有编 b。模型严格按 schema 来，不看函数签名。
2. 代码在 `TOOLS[name](**args)` 这一行抛 `TypeError: add() missing 1 required positional argument: 'b'`。炸的是我的代码，模型那边一切正常。
3. 把这一行包进 try、把错误文本作为 tool 消息回给模型后，模型重试了一次，还是只传 a。错误消息说缺 b，但它的合法参数表里没有 b，想传也传不了。结论：把错误回给模型只能救"模型用错了"，救不了"schema 本身错了"。
4. 连续两次失败后模型放弃工具，自己算出 42，并在回答里写了"加法工具只接受一个参数，我连续调用都报同样的错"。两个问题：简单题它算对了，复杂题它会编；读者看到"工具报错"会觉得产品坏了。所以第 3 章 run_loop 要加一条：工具连续出错直接判失败，不让模型继续解释。

**实验二观察记录（2026-10-22 实测，DeepSeek）**：

1. 漏回传一条 tool 消息，厂商返回 400，原文：`An assistant message with 'tool_calls' must be followed by tool messages responding to each 'tool_call_id'. (insufficient tool messages following tool_calls message)`。这就是规则 2。
2. 同一个错打印了 4 次。因为 except 在 for 循环里、捕获后没有 break，后面 4 轮发的都是同一份坏掉的 messages，每轮都是同一个 400。
3. 结论：400 是请求本身有错，重发多少次都一样，遇到就停。429、500、超时是对方的问题，等一等再发可能就好，这种才值得重试。第 9 章的重试和熔断，第一步就是把错误分成这两类。现在这种"不该重试的重试了 4 次"，加上真实费用就是账单事故。

### 自检

1. 模型"调用"工具时实际发生了什么？谁在执行？
   答：模型返回一段"我想调什么、参数是什么"的结构化数据，你的代码查 TOOLS 字典找到函数执行，结果作为 tool 消息发回去。模型从头到尾没执行任何东西。

3. 两条硬规则各自违反会怎样？

## 第 3 章 Agent 循环

### 这一章解决什么问题

第 2 章末尾那个 `for round_no in range(5)` 已经是 Agent 循环了。这一章做三件事：把它从脚本变成函数，让五个 Agent 都能调；把"撞上限退出"和"正常退出"区分开；把工具出错从"炸掉整个运行"变成"告诉模型一声，它自己想办法"。

做完这章你有了 `runtime.py`，这是第一个会一直留到第 10 章的文件。前两章的 l1、l2 是草稿，这个是产品代码的开头。

### 先想清楚分工

一个 Agent 运行时要分三层，每层只管自己的事：

| 层 | 管什么 | 不管什么 | 文件 |
|---|---|---|---|
| 发请求 | 把 messages 和 tools 发给厂商，拿回 message | 循环、工具执行 | llm.py |
| 循环 | 要工具就执行回传再发，不要就退出；步数上限；工具出错兜底 | 提示词、用哪些工具、模型参数 | runtime.py |
| 业务 | 提示词、工具列表、要问什么、结果怎么用 | 循环怎么跑 | l3_agent.py，以后是各 Agent |

为什么这样分：第 10 章换 LangChain 时只改第一层；加第六个 Agent 时只写第三层；中间那层一次写对，永远不动。线上版的 app/runtime.py 就是中间层，70 行，五个 Agent 共用。

### 3.0 把发请求抽成 llm.py

**做什么**：新建 `llm.py`，把读配置、建 client、`chat()` 搬进去。l2_tools.py 改成 `from llm import chat`，确认还能跑。

**骨架**：

```python
# llm.py
import os
import httpx
from dotenv import load_dotenv

load_dotenv()
BASE_URL = os.environ["LLM_BASE_URL"]
API_KEY = os.environ["LLM_API_KEY"]
MODEL = os.environ["LLM_MODEL"]

client = httpx.Client(base_url=BASE_URL, timeout=60, trust_env=False)
HEADERS = {"Authorization": f"Bearer {API_KEY}"}


def chat(messages: list[dict], tools: list[dict] | None = None) -> dict:
    """发一次请求，返回 choices[0] 里的 message。"""
    body = {"model": MODEL, "messages": messages}
    if tools:
        body["tools"] = tools
    resp = client.post("/chat/completions", headers=HEADERS, json=body)
    resp.raise_for_status()
    return resp.json()
```

**为什么**：

- 你在 l1 和 l2 里已经把这十行抄了两遍。第三遍之前抽出来。规则 4 说"感到痛了再引入"，现在就是痛的时候。
- `tools` 必须是可选参数，默认 None。你 l2 里写的 `tools: list[dict]` 没有默认值，调用时不传会 TypeError。第 1 章那种纯聊天不传 tools，所以要可选。
- llm.py 顶层只有配置和函数定义，没有 print、没有请求。这样别的文件 import 它不会有副作用。这是 2.0 讲的 `__name__` 那个问题的根本解法：共享的东西放一个没有顶层动作的文件里。
- 模块级的 `client` 只建一次，所有调用复用连接。

**验证**：`uv run python l2_tools.py` 跟改之前输出一样。

### 3.1 LoopResult：循环的返回值

**做什么**：在 `runtime.py` 里写 `LoopResult` 类，三个字段：`messages`、`steps`、`hit_max_steps`。

**骨架**：

```python
# runtime.py
from dataclasses import dataclass, field


@dataclass
class LoopResult:
    messages: list[dict] = field(default_factory=list)
    steps: int = 0
    hit_max_steps: bool = False
```

**为什么**：

- 为什么要一个类而不是返回元组 `(messages, True)`：元组靠位置记，`r[1]` 是什么三天后你就忘了。`r.hit_max_steps` 自己会说话。第 4 章还要加 token 字段，类加字段不影响已有代码，元组加一位所有调用方都得改。
- `@dataclass` 是 Python 自带的装饰器，看到类里的字段声明，自动生成 `__init__`、`__repr__`。不用它你要手写 `def __init__(self, messages=None, ...)` 七八行。
- `field(default_factory=list)` 而不是 `= []`：Python 的默认参数只在定义时创建一次，写 `= []` 的话所有 LoopResult 实例共享同一个列表，一个改了全都变。这是 Python 最经典的坑之一，dataclass 直接禁止你这么写，会报错。
- `steps` 数的是模型调用次数，不是工具次数。一次模型调用可能要两个工具，那是一步不是三步。因为钱按模型调用算，上限也按它算。

**验证**：

```bash
uv run python -c "from runtime import LoopResult; r = LoopResult(); r.steps += 1; print(r)"
```

打印 `LoopResult(messages=[], steps=1, hit_max_steps=False)`。

### 3.2 call_tool：工具出错不抛

**做什么**：写 `call_tool(tools: dict, call: dict) -> tuple[str, str | None]`。第一个返回值是给模型看的文本，第二个是记账用的错误，正常时为 None。三种错都要接住：工具名不存在、arguments 不是合法 JSON、工具内部抛异常。

**骨架**：

```python
import json


def call_tool(tools: dict, call: dict) -> tuple[str, str | None]:
    name = call["function"]["name"]
    if name not in tools:
        msg = f"没有名为 {name} 的工具，可用的有：{', '.join(tools)}"
        return msg, msg
    try:
        args = json.loads(call["function"]["arguments"])
    except json.JSONDecodeError as e:
        ...   # 回给模型"参数不是合法 JSON"，第二个返回值也填上
    try:
        result = tools[name](**args)
        return str(result), None
    except Exception as e:
        ...   # 回给模型"工具暂时不可用"，第二个返回值填 repr(e)
```

**为什么**：

- 第 2 章实验一你亲眼看到：工具炸了，异常冒出去，整个脚本死掉。生产里一个工具是网络调用，超时一次就毁掉整个 Agent 运行，太脆。所以工具的错不往外抛，变成一句话回给模型。
- 给模型看的文本和记账的错误要分开。模型看到"工具暂时不可用"就够了，看到完整的 Traceback 反而会把它复述给读者（第 2 章实验一模型就把报错写进了回答）。但 Traceback 对你排障有用，所以第二个返回值留着，第 4 章落库。
- `except Exception` 而不是裸 `except`：裸的会把 Ctrl+C 也吞掉。`Exception` 不包含 KeyboardInterrupt 和 SystemExit。
- 工具名不存在为什么要列出可用的：模型下一轮看到列表就能选对，不列它只能瞎猜。
- `str(result)`：第 2 章说过，tool 消息的 content 必须是字符串。放在这里统一转，调用方不用记。

**验证**：三个错各试一次，不用发请求，直接构造 call 字典：

```python
from runtime import call_tool
from l2_tools import TOOLS
print(call_tool(TOOLS, {"function": {"name": "nope", "arguments": "{}"}}))
print(call_tool(TOOLS, {"function": {"name": "add", "arguments": "{a: 1"}}))
print(call_tool(TOOLS, {"function": {"name": "add", "arguments": '{"a": 1}'}}))
print(call_tool(TOOLS, {"function": {"name": "add", "arguments": '{"a": 1, "b": 2}'}}))
```

前三个第二个返回值非 None，第四个是 `('3', None)`。

### 3.3 run_loop：两个出口

**做什么**：写 `run_loop(send, messages, tools, *, max_steps=6) -> LoopResult`。`send` 是一个函数，签名和 llm.chat 一样：收 messages 和 tools schema，返回厂商的整个响应 dict。`tools` 是名字到函数的字典，schema 由调用方放进 send 里，运行时不管。

**骨架**：

```python
def run_loop(send, messages: list[dict], tools: dict, *, max_steps: int = 6) -> LoopResult:
    r = LoopResult(messages=list(messages))
    for _ in range(max_steps):
        data = send(r.messages)
        msg = data["choices"][0]["message"]
        r.steps += 1
        r.messages.append(msg)                      # 规则 1
        if not msg.get("tool_calls"):
            return r                                # 出口一：正常结束
        for call in msg["tool_calls"]:
            text, error = call_tool(tools, call)
            r.messages.append({                     # 规则 2
                "role": "tool",
                "tool_call_id": call["id"],
                "content": text,
            })
    r.hit_max_steps = True                          # 出口二：撞上限
    return r
```

**为什么**：

- `send` 作为参数传进来，而不是在 runtime.py 里 `from llm import chat`。这叫依赖注入：运行时不知道也不关心请求是 httpx 发的还是 LangChain 发的。第 10 章换底层时 runtime.py 一行不改，只换传进来的 send。测试时也能传一个假的 send，不花钱。
- `send(r.messages)` 只传 messages，tools schema 怎么带是调用方的事。调用方写 `lambda m: chat(m, tools=TOOLS_SCHEMA)` 或者一个小函数把 schema 绑进去。运行时只需要名字到函数的字典来执行。
- 签名里的 `*`：它后面的参数只能用关键字传，`run_loop(send, msgs, tools, 3)` 会报错，必须写 `max_steps=3`。防止以后加参数时位置传错。
- `list(messages)` 复制一份：调用方传进来的列表不该被改。你 l2 里直接 append 到外面的 messages，跑两次就串了。
- 出口一判断 `not msg.get("tool_calls")` 而不是 `finish_reason != "tool_calls"`：有的厂商 finish_reason 不规范，tool_calls 字段有没有更可靠。两个都行，选一个坚持用。
- 出口二在 for 之外：for 正常跑完说明每一轮都要了工具、一次都没正常退出，这才是撞上限。`hit_max_steps` 只在这里置 True。
- 这里**不**接 send 抛出的 HTTPStatusError。400 是配置或请求错，401 是密钥错，重试一万次也没用，应该一路抛到最上面让人看见。工具错和请求错是两类，一类兜住，一类放行。第 9 章再细分 429 和 5xx。
- `error` 这一步先不用。第 4 章它进 steps 表。现在拿着不用是为了签名一次定好。

**验证**：下一步。

### 3.4 l3_agent.py：三个工具加一个坏的

**做什么**：新建 `l3_agent.py`。工具用 l2 的 `get_time`、`add`，再加一个一调就抛异常的 `broken()`。schema 也加上。问一个三个工具都要用到的问题，跑通打印最终回答。然后改 `max_steps=1`，确认 `hit_max_steps` 是 True 并且没有 Traceback。

**骨架**：

```python
from llm import chat
from runtime import run_loop
from l2_tools import get_time, add, TOOLS_SCHEMA


def broken() -> str:
    """查询今天的天气"""
    raise RuntimeError("天气服务挂了")


TOOLS = {"get_time": get_time, "add": add, "broken": broken}
SCHEMA = TOOLS_SCHEMA + [{"type": "function", "function": {
    "name": "broken", "description": "查询今天的天气",
    "parameters": {"type": "object", "properties": {}, "required": []},
}}]


def send(messages):
    return chat(messages, tools=SCHEMA)


if __name__ == "__main__":
    q = [{"role": "user", "content": "现在几点，今天天气怎么样，另外 17 加 25 等于多少"}]
    r = run_loop(send, q, TOOLS, max_steps=6)
    print("steps:", r.steps, "hit_max_steps:", r.hit_max_steps)
    print("最终回答：", r.messages[-1]["content"])
```

**为什么**：

- `broken` 的 description 要写得像真的，模型才会去调它。它调了、炸了、收到"工具暂时不可用"，然后你看它怎么处理：多半是回答里说"天气查不到"，其他两个照答。这就是工具出错不抛的价值：一个工具坏了，另外两个不受影响。
- `send` 包了一层把 SCHEMA 绑进去，这是 3.3 说的"schema 是调用方的事"。
- `max_steps=1` 的测试是在验证出口二。第一轮模型要了三个工具，执行完回传，但循环已经用完一步，不会再发请求。所以 `r.messages[-1]` 是一条 tool 消息不是回答，`hit_max_steps` 是 True。这时调用方该做什么？记一笔失败，不要把半截结果给读者。

**验证**：

- `max_steps=6`：打印 steps 是 2（第一轮要工具，第二轮回答），hit_max_steps False，回答里有时间、有 42、有一句天气查不到。
- `max_steps=1`：steps 是 1，hit_max_steps True，没有 Traceback。

**常见错误**：

- `ImportError: cannot import name 'TOOLS_SCHEMA' from 'l2_tools'`：l2_tools.py 顶层还在跑第 3 步的循环，import 时发了请求然后炸了。把那段放进 `if __name__ == "__main__":`。
- 模型没调 broken：description 太假。换成"查询指定城市今天的天气"并加一个 city 参数试试。
- 回答里出现"RuntimeError"字样：call_tool 把异常原文给模型了。给模型的文本不该带 Traceback。

### 这一章解决什么问题

第 3 章的五行打印，进程一退就没了。产品要回答的问题是：这个读者的提问花了多少钱？这本书的导读为什么失败？模型最后一步给了什么？要回答就得把每次运行和每一步存下来。这一章把 print 换成写数据库。

数据库用 SQLite：Python 自带，一个文件就是一个库，不用装任何东西。SQL 语法和 Postgres 几乎一样，线上版换成 Postgres 只换连接那几行。

### 先看懂两张表

一父一子。父表一次运行一条，子表一次运行里的每一步一条。

**runs 表**

| 字段 | 类型 | 含义 | 为什么要 |
|---|---|---|---|
| id | INTEGER 主键自增 | run_id | 子表靠它关联 |
| trace_id | TEXT 非空 | 跨系统追踪 id | 线上拿一个 id 能从 Go 日志查到这里 |
| agent | TEXT 非空 | guide / quiz / tutor | 按 Agent 统计用量 |
| model | TEXT 非空 | 模型名 | 算钱要知道单价 |
| status | TEXT 默认 running | running / done / failed | 第 9 章靠 running 找卡住的 |
| input_tokens | INTEGER 默认 0 | 总输入 token | 算钱 |
| output_tokens | INTEGER 默认 0 | 总输出 token | 算钱 |
| cost | TEXT | 成本，存 Decimal 的字符串 | SQLite 没有 NUMERIC，存字符串读回来再转 |
| latency_ms | INTEGER | 总耗时 | 看慢不慢 |
| steps | INTEGER 默认 0 | 模型调了几次 | 看有没有绕圈 |
| error | TEXT | 失败原因 | 排障 |
| created_at | TEXT 默认当前时间 | 开始时间 | 第 9 章算"卡了多久" |
| finished_at | TEXT | 结束时间 | 空着就是没结束 |

**steps 表**

| 字段 | 含义 | 为什么要 |
|---|---|---|
| run_id | 属于哪次运行 | 外键 |
| seq | 第几行，从 1 起 | 顺序 |
| kind | llm 或 tool | 分开统计 |
| name | 模型名或工具名 | 看调了什么 |
| input | llm 存完整消息列表，tool 存参数 | 坏样本的唯一来源，改提示词全靠回看它 |
| output | llm 存模型回复原文，tool 存回给模型的文本 | 同上 |
| input_tokens / output_tokens | 这一步的 token，tool 步为 0 | 每步成本 |
| latency_ms | 这一步耗时 | 哪步慢 |
| error | 工具的错误原文 | 3.2 那个 repr(e) 落在这里 |
| UNIQUE (run_id, seq) | 同一次运行序号不重 | 防重试写重 |

四个设计决定，记住为什么：

- **run 先建再跑**。开始就 INSERT 一条 running，结束再 UPDATE。进程中途被杀，表里会留一条 running，这是第 9 章发现"卡住"的依据。等结束再 INSERT，失败了什么都查不到。
- **钱不用 float**。浮点加一万次有误差，0.1 + 0.2 不等于 0.3。用 Decimal 算，SQLite 没有 NUMERIC 就存字符串。
- **trace_id 和 run_id 不是一回事**。run_id 是这张表的主键，只在这个库里有意义。trace_id 是跨系统的，Go 生成传过来，Python 记进表和日志。一个 trace 下可能有多个 run。没传就自己生成，不能为空。
- **失败也要记 token**。模型调了八轮最后一步挂了，钱已经花了。线上版曾在失败分支写 input_tokens=0，账对不上。这一章先把数据结构定好，第 5 章用上下文管理器保证失败分支也记。

### SQLite 十分钟够用

你没用过 SQLite，先记这几样：

```python
import sqlite3
conn = sqlite3.connect("runs.db")          # 文件不存在就创建
conn.row_factory = sqlite3.Row             # 查询结果能按列名取，row["agent"]
cur = conn.execute("INSERT INTO runs (agent) VALUES (?)", ("guide",))   # ? 是占位符，值用元组传
conn.commit()                              # 不 commit 不落盘
cur.lastrowid                              # 刚插入那行的 id
row = conn.execute("SELECT * FROM runs WHERE id = ?", (1,)).fetchone()
rows = conn.execute("SELECT * FROM steps WHERE run_id = ?", (1,)).fetchall()
```

- `?` 占位符必须用，不能 f-string 拼 SQL。拼的话值里有个单引号就坏，恶意的值能删库。这叫 SQL 注入，所有数据库都一样。
- 值是元组，一个值也要写 `("guide",)`，逗号不能少，不然 Python 当成括号表达式。
- `commit()` 之后别的连接才看得到。忘了 commit 是最常见的"明明插了为什么查不到"。

### 4.1 建表

**做什么**：新建 `runs.py`。写 `connect()` 返回连接，写 `init_db()` 建两张表。库文件叫 `runs.db`，加进 .gitignore。

**骨架**：

```python
# runs.py
import sqlite3

DB_PATH = "runs.db"

SCHEMA = """
CREATE TABLE IF NOT EXISTS runs (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    trace_id      TEXT NOT NULL,
    agent         TEXT NOT NULL,
    model         TEXT NOT NULL,
    status        TEXT NOT NULL DEFAULT 'running',
    input_tokens  INTEGER NOT NULL DEFAULT 0,
    output_tokens INTEGER NOT NULL DEFAULT 0,
    cost          TEXT NOT NULL DEFAULT '0',
    latency_ms    INTEGER,
    steps         INTEGER NOT NULL DEFAULT 0,
    error         TEXT,
    created_at    TEXT NOT NULL DEFAULT (datetime('now')),
    finished_at   TEXT
);
CREATE TABLE IF NOT EXISTS steps (
    ...   -- 照上面的表自己写，别忘了最后的 UNIQUE (run_id, seq)
);
"""


def connect() -> sqlite3.Connection:
    conn = sqlite3.connect(DB_PATH)
    conn.row_factory = sqlite3.Row
    return conn


def init_db() -> None:
    with connect() as conn:
        conn.executescript(SCHEMA)
```

**为什么**：

- `IF NOT EXISTS`：init_db 可以放心反复调，表在就跳过。没有它第二次跑报"table already exists"。
- `executescript` 而不是 `execute`：execute 一次只能跑一条 SQL，建两张表要 script。
- `with connect() as conn`：SQLite 的连接支持 with，退出时自动 commit，出异常自动回滚。注意它不关连接，只管事务。练习里连接随用随建没关系，第 7 章做服务时再谈复用。
- 建表 SQL 放在一个字符串常量里而不是写进函数：以后看表结构就看这一块，不用翻函数。线上版放在 migrations/001_runs.sql，是同一个思路。
- `runs.db` 进 .gitignore：数据库文件是运行产物，不是代码。

### 4.2 算钱

**做什么**：写价格字典 `PRICES` 和 `cost_of(model, input_tokens, output_tokens) -> Decimal`。

**骨架**：

```python
from decimal import Decimal

# 每百万 token 的价格，单位元。查厂商定价页填，调价改这里。
PRICES = {
    "deepseek-chat": (Decimal("2.0"), Decimal("3.0")),   # (输入, 输出)
}


def cost_of(model: str, input_tokens: int, output_tokens: int) -> Decimal:
    pin, pout = PRICES.get(model, (Decimal(0), Decimal(0)))
    return ...   # (输入 token × 输入单价 + 输出 token × 输出单价) / 1_000_000
```

**为什么**：

- `Decimal("2.0")` 用字符串构造，不用 `Decimal(2.0)`。浮点 2.0 本身是精确的，但 `Decimal(0.1)` 会得到 0.1000000000000000055511151231257827，因为 0.1 在二进制里存不准。字符串构造永远精确。养成习惯，一律字符串。
- `.get(model, (0, 0))`：没登记价格的模型算 0 而不是报错。记账不该让运行失败。但 0 会让账目漏掉，第 7 章做服务时可以在启动时检查模型有没有价格。
- 除以 `1_000_000`：下划线是 Python 允许的数字分隔符，纯粹为了人眼好读。

**验证**：

```bash

```

### 4.3 三个写入函数

**做什么**：写 `start_run`、`add_step`、`finish_run`。

**骨架**：

```python
import json
import time
import uuid


def new_trace_id() -> str:
    return uuid.uuid4().hex


def start_run(*, trace_id: str, agent: str, model: str) -> int:
    with connect() as conn:
        cur = conn.execute(
            "INSERT INTO runs (trace_id, agent, model) VALUES (?, ?, ?)",
            (trace_id, agent, model),
        )
        return cur.lastrowid


def add_step(run_id: int, seq: int, kind: str, name: str, *,
             input=None, output=None, input_tokens: int = 0, output_tokens: int = 0,
             latency_ms: int | None = None, error: str | None = None) -> None:
    with connect() as conn:
        conn.execute(
            "INSERT INTO steps (...) VALUES (...)",     # 十个字段，自己数
            (run_id, seq, kind, name,
             json.dumps(input, ensure_ascii=False, default=str),
             json.dumps(output, ensure_ascii=False, default=str),
             input_tokens, output_tokens, latency_ms, error),
        )


def finish_run(run_id: int, *, status: str, model: str, input_tokens: int, output_tokens: int,
               latency_ms: int, steps: int, error: str | None = None) -> None:
    cost = cost_of(model, input_tokens, output_tokens)
    with connect() as conn:
        conn.execute(
            """UPDATE runs SET status=?, input_tokens=?, output_tokens=?, cost=?,
               latency_ms=?, steps=?, error=?, finished_at=datetime('now') WHERE id=?""",
            (status, input_tokens, output_tokens, str(cost), latency_ms, steps, error, run_id),
        )
```

**为什么**：

- 三个函数的 `*` 把参数变成只能关键字传。`finish_run(3, "done", ...)` 这种位置传法在八个参数里必错，强制写名字。
- `start_run` 只插三个字段，其余全靠表的 DEFAULT。status 默认 running、token 默认 0，这就是"先建再跑"。
- `add_step` 的 input 和 output 用 `json.dumps` 转成字符串存。SQLite 没有 JSON 类型，存文本。`default=str` 是遇到 json 不认识的类型（比如 Decimal、datetime）就调 str，别炸。`ensure_ascii=False` 让你直接打开库文件也能看中文。
- `finish_run` 里算 cost 而不是让调用方算：调用方只知道 token，单价是记账模块的事。cost 存 `str(cost)`，读回来 `Decimal(row["cost"])`。
- `uuid.uuid4().hex` 是 32 位随机十六进制，没有横线。trace_id 要的就是一个全局不重复的字符串。

**验证**：

```bash

init_db()
rid = start_run(trace_id=new_trace_id(), agent='test', model='deepseek-chat')
add_step(rid, 1, 'llm', 'deepseek-chat', input=[{'role':'user','content':'hi'}], output={'content':'hello'}, input_tokens=5, output_tokens=2, latency_ms=800)
add_step(rid, 2, 'tool', 'add', input={'a':1,'b':2}, output='3', latency_ms=1)
finish_run(rid, status='done', model='deepseek-chat', input_tokens=5, output_tokens=2, latency_ms=801, steps=1)

```

打印一个数字。然后 `sqlite3 runs.db "select id, status, cost, steps from runs; select run_id, seq, kind, name, error from steps;"` 看两张表的内容。

**常见错误**：

- `sqlite3.IntegrityError: UNIQUE constraint failed: steps.run_id, steps.seq`：同一个 run 写了两次 seq 相同的步。
- `sqlite3.OperationalError: no such table`：忘了 init_db。
- `ProgrammingError: Incorrect number of bindings`：VALUES 里的 `?` 个数和元组长度不一致。数一遍。

### 4.4 改 run_loop：打印换落库

**做什么**：三处改动。`LoopResult` 加 `input_tokens`、`output_tokens` 两个字段。`run_loop` 签名加 `run_id` 和 `model_name`，两个都放 `*` 后面。循环里每次模型调用、每次工具调用各 `add_step` 一条，llm 步记 token 和耗时，tool 步记错误。3.5 的两行 print 可以留着也可以删，建议留着改成只在调试时开。

**骨架**：

```python
import time
from runs import add_step


def run_loop(send, messages: list[dict], tools: dict, *,
             run_id: int, model_name: str, max_steps: int = 6) -> LoopResult:
    r = LoopResult(messages=list(messages))
    seq = 0
    for _ in range(max_steps):
        t1 = time.perf_counter()
        data = send(r.messages)
        latency = int((time.perf_counter() - t1) * 1000)
        msg = data["choices"][0]["message"]
        usage = data.get("usage") or {}
        it, ot = usage.get("prompt_tokens", 0), usage.get("completion_tokens", 0)
        r.steps += 1
        r.input_tokens += it
        r.output_tokens += ot
        seq += 1
        add_step(run_id, seq, "llm", model_name,
                 input=r.messages, output=msg,
                 input_tokens=it, output_tokens=ot, latency_ms=latency)
        r.messages.append(msg)
        if not msg.get("tool_calls"):
            return r
        for call in msg["tool_calls"]:
            t2 = time.perf_counter()
            text, error = call_tool(tools, call)
            seq += 1
            add_step(run_id, seq, "tool", call["function"]["name"],
                     input=call["function"]["arguments"], output=text,
                     latency_ms=int((time.perf_counter() - t2) * 1000), error=error)
            r.messages.append({"role": "tool", "tool_call_id": call["id"], "content": text})
    r.hit_max_steps = True
    return r
```

**为什么**：

- `seq` 和 `r.steps` 是两个计数器。steps 数模型调用次数，是上限和账单的口径；seq 数表里的行数，llm 和 tool 都算。一轮要三个工具，steps 加 1，seq 加 4。
- `add_step` 的 llm 步在 `r.messages.append(msg)` **之前**调：input 存的是"发给模型时的消息列表"，不含它这次的回复。回复在 output 里。顺序反了 input 会多一条。
- `time.perf_counter()` 而不是 `time.monotonic()`：两个都单调，perf_counter 精度更高，测毫秒级用它。第 1 章用 monotonic 测秒级也没错。
- `usage.get(...) or {}`：流式和某些厂商的返回可能没有 usage，缺了记 0，不能让记账炸掉运行。
- 为什么 `run_id` 由调用方传进来而不是 run_loop 自己 start_run：一次 Agent 运行可能不止一个 run_loop，比如导读是"读资料"循环加"写导读"结构化输出两段，它们共用一个 run。谁开 run 谁负责关，run_loop 只在里面记步。
- `model_name` 也传进来：run_loop 不知道 send 背后用的什么模型，依赖注入的代价就是信息要显式传。

**验证**：下一步的 l4_run.py。

### 4.5 读回来

**做什么**：写 `get_run(run_id) -> dict | None`，一条 run 加它的所有 steps，steps 按 seq 排序。input 和 output 要 `json.loads` 回来。

```python
def get_run(run_id: int) -> dict | None:

        if row is None:
            return None
        run = dict(row)
        rows = conn.execute("SELECT * FROM steps WHERE run_id = ? ORDER BY seq", (run_id,)).fetchall()
```

## 第 5 章 上下文管理器收尾

### 这一章解决什么问题

看你 l4_run.py 的 `run_agent`：start_run、计时、run_loop、finish_run，十行。每个 Agent 入口都要抄这十行。线上版抄了 8 次，其中一次把失败分支的 token 写成了 0。

更大的问题：它没有 try。run_loop 里 send 抛了 HTTP 错，finish_run 跑不到，表里留一条 running。第 4 章如果你中途杀过进程或 send 炸过，表里那条 running 就是这么来的。要修就得加 try、except 里 finish_run failed、再 raise，变成十五行，每个 Agent 抄十五行。

Python 对"进入做一件事，退出无论成败都做另一件事"有标准形状：`with`。这一章把那十五行压成一个 with，以后 Agent 代码里只剩业务。

### with 和 yield 是怎么回事

你已经用过 with 两次：`with open(...)` 退出时关文件，`with connect() as conn` 退出时提交或回滚。它们的共同点是退出时的动作一定执行，块里 raise 了也执行。

自己写一个 with 能用的东西，最简单的办法是 `contextlib.contextmanager` 装饰一个带 `yield` 的函数：

```python
from contextlib import contextmanager

@contextmanager
def demo():
    print("进入")
    yield "交出去的东西"
    print("退出")

with demo() as x:
    print("块里，拿到", x)
```

打印顺序：进入、块里，拿到 交出去的东西、退出。`yield` 是函数的暂停点：跑到 yield 停下，把 yield 后面的值交给 `as x`，然后执行 with 块；块结束再从 yield 那一行继续往下。

块里 raise 了会怎样：异常从 yield 那一行冒出来。所以把 yield 包进 try，就能在 except 里收尾：

```python
from contextlib import contextmanager

@contextmanager
def demo():
    print("进入")
    try:
        yield
    except Exception as e:
        print("块里炸了：", e)
        raise
    else:
        print("正常退出")
```

三个要点，这一章全部围绕它们：

- **yield 交出去一个对象**，块里把 token、步数记在这个对象上。退出时成功和失败两条路读的是同一个对象，不会再出现"失败记 0"。
- **except 里必须 `raise`**。上下文管理器的职责是收尾，不是吞错。吞了上层以为成功。
- **用 except 加 else，不用 finally**。finally 分不清成功失败，还得自己立 flag。

先把上面第二段 demo 在 `-c` 里跑一遍，块里分别写 `pass` 和 `raise ValueError("test")`，看两种打印顺序。10 秒，但跑过之后下面的代码就不是魔法了。

### 5.1 Run：记账本

**做什么**：在 runs.py 追加 `Run` 类。字段 `id`、`model`、`seq`、`input_tokens`、`output_tokens`、`status`。两个方法：`add_usage(usage)` 累 token 并把 usage 原样返回；`ste\p(kind, name, *, usage=None, input=None, output=None, latency_ms=None, error=None)` seq 自增后调 add_step。

**骨架**：

```python
class Run:
    """一次执行的记账本。with tracked_run(...) as run 交出来的就是它。"""

    def __init__(self, run_id: int, model: str):
        self.id = run_id
        self.model = model
        self.seq = 0
        self.input_tokens = 0
        self.output_tokens = 0
        self.status = "done"       # 正常退出时写的状态，块里可以改成 aborted

    def add_usage(self, usage: dict) -> dict:
        self.input_tokens += usage.get("prompt_tokens", 0)
        self.output_tokens += ...
        return usage

    def step(self, kind: str, name: str, *, usage: dict | None = None,
             input=None, output=None, latency_ms: int | None = None, error: str | None = None) -> int:
        self.seq += 1
        usage = usage or {}
        add_step(...)              # 十个参数，token 从 usage 里取
        return self.seq
```

**为什么**：

- 这次不用 dataclass，用普通类。它有行为（两个方法）而且 `__init__` 要接 run_id 这种和字段名不同的参数，dataclass 反而别扭。dataclass 适合纯数据，像 LoopResult。
- `seq` 从 LoopResult 和 run_loop 的局部变量搬到这里。第 4 章说"一次 Agent 运行可能有多段 run_loop 共用一个 run"，seq 要跨段连续，只能挂在 run 上。
- `add_usage` 返回 usage 是为了一行写两件事：`run.step("llm", ..., usage=run.add_usage(data["usage"]))`，累总数的同时这一步也记上。
- `status` 默认 done，块里可以改。第 8 章问答流式时读者中途断开，不算失败但也没完成，Agent 把它改成 aborted。

**验证**：


### 5.2 tracked_run：with 包住一次执行

**做什么**：runs.py 追加 `tracked_run(*, trace_id=None, agent, model)`，照"with 和 yield"那一段的形状。进入时 start_run 建 Run，退出时按成功失败调 finish_run。

**骨架**：

```python
import time
from contextlib import contextmanager


@contextmanager
def tracked_run(*, trace_id: str | None = None, agent: str, model: str):
    run = Run(start_run(trace_id=trace_id or new_trace_id(), agent=agent, model=model), model)
    t0 = time.perf_counter()
    try:
        yield run
    except Exception as e:
        finish_run(run.id, status="failed", model=model,
                   input_tokens=run.input_tokens, output_tokens=run.output_tokens,
                   latency_ms=int((time.perf_counter() - t0) * 1000), steps=run.seq, error=repr(e))
        raise
    else:
        finish_run(...)            # status 用 run.status，其余和上面一样，没有 error
```

**为什么**：

- `trace_id or new_trace_id()`：没传就自己生成，表里永远不空。
- 两个分支的 token 都从 `run` 上读。这就是 线上版那个"失败记 0"bug 的根治：没有第二份数据可以写错。
- except 里 `raise` 不写 `raise e`：裸 raise 保留原始调用栈，报错指向真正炸的那行；`raise e` 会把栈截到这一行。
- `steps=run.seq`：第 4 章 run 表的 steps 列存的是模型调用次数，现在 Run 上只有 seq（含 tool 步）。两个口径选一个：这里先用 seq，笔记里记下这个差别，第 10 章对照 线上版时再定。
- 不用 finally：finally 里不知道是成功还是失败，得在 try 前立一个 `ok = False`、块末尾改 True，多两行还容易忘。except 加 else 天然分开。

**验证**：三种情况各跑一次，不用模型：

```bash
uv run python -c "

init_db()
with tracked_run(agent='t1', model='deepseek-chat') as run:
    run.step('llm', 'x', usage=run.add_usage({'prompt_tokens': 7, 'completion_tokens': 1}))
print('t1 ok', run.id)
with tracked_run(agent='t2', model='deepseek-chat') as run:
    run.status = 'aborted'
print('t2 ok', run.id)
try:
    with tracked_run(agent='t3', model='deepseek-chat') as run:
        run.add_usage({'prompt_tokens': 99, 'completion_tokens': 9})
        raise ValueError('boom')
except ValueError as e:
    print('t3 raised', e, run.id)
"
```

然后查表：

```bash
sqlite3 runs.db "select id, agent, status, input_tokens, steps, error from runs where agent in ('t1','t2','t3');"
```

预期：t1 是 done、7、1；t2 是 aborted；t3 是 failed、99、error 含 boom。**t3 的 input_tokens 必须是 99 不是 0**，这是这一章的核心验证。

**常见错误**：

- `AttributeError: 'generator' object has no attribute '__enter__'`：忘了 `@contextmanager`。
- t3 没打印 raised，直接 Traceback 到顶：except 里 raise 了但你外面没接。预期行为，外层要接。
- t3 打印了 raised 但表里是 running：except 里 finish_run 之前就炸了，多半是参数名拼错。
- `RuntimeError: generator didn't stop after throw()`：except 里没有 raise 也没有 return，生成器不知道该怎么继续。

### 5.3 改 run_loop：接 Run，不接 run_id

**做什么**：run_loop 签名改成 `run_loop(send, messages, tools, *, run: Run, max_steps=6)`，去掉 run_id 和 model_name。内部 add_step 全换成 `run.step`，token 用 `run.add_usage`。LoopResult 去掉两个 token 字段和 seq 局部变量，token 和 seq 现在只在 Run 上。

**骨架**（只给改动的几行）：

```python
from runs import Run

def run_loop(send, messages: list[dict], tools: dict, *, run: Run, max_steps: int = 6) -> LoopResult:
    ...
        usage = run.add_usage(data.get("usage") or {})
        run.step("llm", run.model, input=r.messages, output=msg, usage=usage, latency_ms=latency)
    ...
```

### 5.4 l5_ctx.py：三种情况加重写 run_agent

**做什么**：新建 `l5_ctx.py`。先把 l4 的 `run_agent` 用 tracked_run 重写，撞上限的情况在 with 块里 raise，让它走失败分支：

```python
from llm import MODEL
from runtime import run_loop
from runs import init_db, tracked_run, get_run
from l3_agent import TOOLS, send


def run_agent(question: str, *, max_steps: int = 6) -> int:
    with tracked_run(agent="l5", model=MODEL) as run:
        r = run_loop(send, [{"role": "user", "content": question}], TOOLS, run=run, max_steps=max_steps)
        if r.hit_max_steps:
            raise RuntimeError("撞到步数上限")
    return run.id
```

对比 l4 的十行：业务只剩三行，记账一行看不见。然后在 `if __name__` 里跑三种情况：正常 max_steps=6；max_steps=1 外面用 try 接住 RuntimeError；再来一次正常的但块里 `run.status = "aborted"`。每次打印 run.id，最后 get_run 三条，打印 status、token、error。

**为什么**：

- `return run.id` 在 with 外面：with 块正常结束才走到这，此时 finish_run 已经跑完。写在块里也行（自检第 1 题），但放外面更清楚。
- 撞上限用 raise 而不是 `run.status = "failed"`：失败要带 error 原因，else 分支不写 error。而且上层要知道失败，raise 是唯一能让它知道的办法。
- 这个 `run_agent` 的形状就是以后每个 Agent 入口的形状。五个 Agent 教程里 `generate_guide(book, *, run)` 那种签名，run 就是从这里的 with 交出去的。

**验证**：表里三条新 run，分别 done、failed 带"撞到步数上限"、aborted。failed 那条 token 非零。

### 自检

1. 块里 `return` 了，yield 后面的代码还跑吗？
   答：跑。return 触发生成器正常退出，走 else。所以 `return run.id` 写在块里也能正确收尾。
2. 为什么 `raise` 不写成 `raise e`？
   答：裸 raise 保留原始调用栈，报错指向真正炸的那行。
3. except 里 finish_run 自己也抛了，会怎样？
   答：新异常盖住原异常，上层看到的是数据库错误而不是业务错误，而且记录停在 running。要不要防：生产里要，把 finish_run 包一层 try 打日志；练习里不防，先知道有这个坑。
4. 为什么 token 要记在 Run 上而不是 LoopResult 上？
   答：成功和失败两条路都要读它。LoopResult 在块里，块炸了拿不到；Run 在 with 外面建的，两条路都能读。

## 第 6 章 结构化输出与打回重试

### 这一章解决什么问题

导读、复习题、知识图谱的结果要存进数据库，必须是固定结构的 JSON，不能是一段散文。第 1 章 1.3 你让模型"只输出 JSON"，5 次成功 5 次，但那是一个字段的小结构。出题要几十道题、每题四个选项加答案加依据，靠提示词约束，模型会少字段、改类型、外面包一层 markdown 代码块。线上版的出题和导图都栽过。

这一章用第 2 章的工具调用协议解决它：把你要的结构定义成一个"工具"的参数 schema，强制模型调它，arguments 就是你要的 JSON。然后两层校验，不过就把错误原话发回去让它改，最多三次。

学完这章，运行时的前半段就齐了：会调模型、会循环、会记账、会要结构。五个 Agent 教程从这里开始可以并行学。

### 先看懂做法

**为什么借工具调用**。模型"输出 JSON"是在自由文本里写 JSON，厂商不保证格式。模型"调用工具"时 arguments 字段厂商会按你给的 JSON Schema 约束生成，可靠得多。而且请求里加 `tool_choice` 可以强制它必须调这个工具，不许自由回答。DeepSeek 不支持 OpenAI 自家的 `response_format: json_schema`，所以 线上版全走这条路，LangChain 的 `with_structured_output(method="function_calling")` 做的就是这件事。

**两层校验**：

| 层 | 查什么 | 谁写 | 工具 |
|---|---|---|---|
| 格式 | 字段齐不齐、类型对不对 | 运行时，所有 Agent 一样 | pydantic 的 `model_validate` |
| 质量 | 格式对了但内容不行：题太少、答案越界、依据找不到 | 每个 Agent 自己 | 一个 `check(obj) -> list[str]` 函数，运行时只负责调它 |

**打回**：任何一层不过，把模型那条回复放回 messages（规则 1），跟一条 tool 消息说"不合格：原因。请修正后重新完整输出"（规则 2），再发。通常一两次就好，上限 3 次，超过算失败。

**一个坑**：模型吐的 arguments 不是合法 JSON 时，在厂商那边照样算一次 tool_call，照样要回 tool 消息，否则下一次 400。而且一次回复可能有多个 tool_call，打回前每一个 id 都要回上。第 2 章实验二那个 400 在这里会以新面目出现。

### 6.0 两件准备

**清理 runtime.py**。你的文件里留着第 3、4 章两版注释掉的 run_loop，还有 LoopResult 里两个没人用的 token 字段、run_loop 里没人用的 `seq` 变量和 `it, ot` 那行。现在删干净：一个 LoopResult 三个字段，一个 call_tool，一个 run_loop。旧版本在 git 历史里，想看 `git show d1b9e99:runtime.py`。产品文件不留注释掉的代码，这是规矩。

**给 chat 加 tool_choice**。llm.py 的 chat 签名改成：

```python
def chat(messages: list[dict], tools: list[dict] | None = None, tool_choice: dict | None = None) -> dict:
    body = {"model": MODEL, "messages": messages}
    if tools:
        body["tools"] = tools
    if tool_choice:
        body["tool_choice"] = tool_choice
    ...
```

`tool_choice` 的格式是 `{"type": "function", "function": {"name": "Quiz"}}`，意思是"必须调这个"。不传就是默认的 auto，模型自己决定。

**装 pydantic**：`uv add pydantic`。

### pydantic 十分钟够用

pydantic 是 Python 最常用的数据校验库，FastAPI 和 LangChain 都建在它上面。你定义一个类，它负责"一个字典是不是长这样"：

```python
from pydantic import BaseModel, Field, ValidationError

class Question(BaseModel):
    stem: str = Field(description="题干，一句话")
    options: list[str] = Field(description="四个选项")
    answer: int = Field(description="正确选项的下标，0 到 3")

q = Question.model_validate({"stem": "RAG 是什么", "options": ["a", "b", "c", "d"], "answer": 1})
q.stem                    # 按属性取，IDE 能补全
q.model_dump()            # 变回字典

Question.model_validate({"stem": "x"})         # 抛 ValidationError：options 和 answer 缺失
Question.model_json_schema()                  # 生成 JSON Schema 字典，和第 2 章手写的 parameters 一样的格式
```

三个要点：

- `Field(description=...)` 的描述会进 JSON Schema，发给模型。所以描述是写给模型看的，决定它怎么填。五个 Agent 教程说"schema 就是产品定义"，指的是这个。
- `ValidationError` 的信息很具体，带字段路径和原因。这就是要发回给模型的东西。
- `model_json_schema()` 省掉第 2 章手写 schema 的活。第 10 章 LangChain 的 `@tool` 也是靠它。

**验证**：把上面的 Question 在 `-c` 里跑一遍，看 `model_json_schema()` 打出来长什么样，和你 l2_tools.py 里手写的 add 的 parameters 比一比。

### 6.1 pydantic_to_tool

**做什么**：新建 `structured.py`，写 `pydantic_to_tool(model_class) -> dict`，把一个 pydantic 类变成第 2 章那种工具描述。

**骨架**：

```python
# structured.py
from pydantic import BaseModel


def pydantic_to_tool(model_class: type[BaseModel]) -> dict:
    schema = model_class.model_json_schema()
    return {
        "type": "function",
        "function": {
            "name": model_class.__name__,
            "description": model_class.__doc__ or f"输出 {model_class.__name__}",
            "parameters": schema,
        },
    }
```

**为什么**：

- 工具名用类名，调用方不用再起名字。`tool_choice` 里也用这个名字。
- description 用类的 docstring。所以 schema 类要写 docstring，告诉模型这个结构是干什么的。
- `type[BaseModel]` 这个标注的意思是"参数是一个类，不是实例"。

**验证**：

```bash
uv run python -c "
from pydantic import BaseModel, Field
from structured import pydantic_to_tool
import json
class Q(BaseModel):
    '''一道题'''
    stem: str = Field(description='题干')
    answer: int
print(json.dumps(pydantic_to_tool(Q), ensure_ascii=False, indent=2))
"
```

看到 name 是 Q、description 是"一道题"、parameters 里有 stem 和 answer，带 required。

### 6.2 invoke_structured：核心循环

**做什么**：structured.py 追加 `invoke_structured(send, messages, schema, *, check=None, run, attempts=3)`。每次尝试 `run.step` 记一条，合格返回 pydantic 对象，三次都不合格抛 RuntimeError。

**骨架**：

```python
import json
import time
from pydantic import ValidationError
from runs import Run


def invoke_structured(send, messages: list[dict], schema: type[BaseModel], *,
                      check=None, run: Run, attempts: int = 3):
    tool = pydantic_to_tool(schema)
    choice = {"type": "function", "function": {"name": tool["function"]["name"]}}
    msgs = list(messages)
    err = "没有尝试"
    for attempt in range(1, attempts + 1):
        t1 = time.perf_counter()
        data = send(msgs, tools=[tool], tool_choice=choice)
        msg = data["choices"][0]["message"]
        usage = run.add_usage(data.get("usage") or {})
        latency = int((time.perf_counter() - t1) * 1000)
        msgs.append(msg)                                   # 规则 1
        calls = msg.get("tool_calls") or []

        if not calls:                                      # 没按要求调工具，自由回答了
            err = "没有调用工具，直接输出了文本"
            run.step("llm", run.model, input=msgs[:-1], output=msg, usage=usage, latency_ms=latency, error=err)
            msgs.append({"role": "user", "content": f"不合格：{err}。请调用 {tool['function']['name']} 工具输出。"})
            continue

        obj, err = None, None
        try:
            obj = schema.model_validate(json.loads(calls[0]["function"]["arguments"]))
            problems = check(obj) if check else []
            if problems:
                err = "；".join(problems)
        except json.JSONDecodeError as e:
            err = f"参数不是合法 JSON：{e}"
        except ValidationError as e:
            err = ...      # 把 e.errors() 里每条的 loc 和 msg 拼成一句，见下面"为什么"

        run.step("llm", run.model, input=msgs[:-1], output=msg, usage=usage, latency_ms=latency, error=err)
        if err is None:
            return obj

        for c in calls:                                    # 规则 2：每个 id 都回
            msgs.append({"role": "tool", "tool_call_id": c["id"],
                         "content": f"不合格：{err}。请修正后重新完整输出。"})
    raise RuntimeError(f"{attempts} 次都不合格，最后一次：{err}")
```

**为什么**：

- `msgs = list(messages)` 复制，和 run_loop 一样，不改调用方的列表。
- `tool_choice` 强制调工具，但模型偶尔还是会无视它直接回文本。这时没有 tool_call id，不能回 tool 消息，只能追加一条 user 消息要求重来。这个分支 线上版第一版没写，导图 Agent 遇到过。
- `run.step` 在合格和不合格时都记，不合格的 output 存整份模型回复、error 存原因。这是"坏样本的唯一来源"：以后改提示词，就是去 steps 表里看这些不合格的输出长什么样。
- `input=msgs[:-1]`：记"发给模型时"的消息列表，不含它这次的回复，和 run_loop 一致。
- ValidationError 的处理：`e.errors()` 返回一个列表，每条有 `loc`（字段路径，元组）和 `msg`。拼成 `"questions.2.answer: Input should be a valid integer"` 这种。pydantic 的 `str(e)` 太长太乱，模型看不懂，拼短的。写法提示：`"; ".join(f"{'.'.join(map(str, x['loc']))}: {x['msg']}" for x in e.errors())`。
- 质量校验 `check` 是可选参数，返回问题列表，空列表表示合格。运行时不知道也不关心规则是什么，这是运行时和 Agent 的分界。
- 打回的 tool 消息对**每一个** call 都回。模型一般只调一次，但万一调了两次，漏一条就是 400。
- 为什么是 `RuntimeError` 而不是返回 None：三次不合格是真失败，要走 tracked_run 的 except 分支记 failed。返回 None 调用方容易忘了检查。

**验证**：下一步的 Quiz 跑通才算。

### 6.3 Quiz schema 和质量校验

**做什么**：新建 `l6_struct.py`，定义 `Question` 和 `Quiz` 两个 pydantic 类，写 `check_quiz(quiz) -> list[str]`：至少 3 题、每题 4 个选项、answer 在 0 到 3。

**骨架**：

```python
from pydantic import BaseModel, Field


class Question(BaseModel):
    stem: str = Field(description="题干，一句话，考察理解不考察背诵")
    options: list[str] = Field(description="四个选项的文字，不带 A B C D 前缀")
    answer: int = Field(description="正确选项的下标，0 到 3")


class Quiz(BaseModel):
    """根据给定文章出的一组选择题"""
    points: list[str] = Field(description="文章的 3 到 5 个要点，每条一句话")
    questions: list[Question] = Field(description="选择题列表")


def check_quiz(quiz: Quiz) -> list[str]:
    problems = []
    if len(quiz.questions) < 3:
        problems.append(f"至少 3 题，现在 {len(quiz.questions)} 题")
    for i, q in enumerate(quiz.questions, 1):
        if len(q.options) != 4:
            problems.append(...)
        if not 0 <= q.answer <= 3:
            problems.append(...)
    return problems
```

**为什么**：

- 格式校验（answer 是 int）pydantic 管，质量校验（answer 在 0 到 3）check 管。为什么 0 到 3 不用 pydantic 的 `Field(ge=0, le=3)`：可以用，而且更好。但这一章要你体会两层的分界，先放 check 里，做完 6.5 再挪过去对比。
- 错误信息要带编号和数字："第 2 题 5 个选项，要 4 个"。模型看到具体位置才能改对。笼统说"选项数不对"它会全部重写。
- `enumerate(quiz.questions, 1)` 从 1 数，报错给人和模型看都是"第 1 题"不是"第 0 题"。

### 6.4 跑 10 次，看统计

**做什么**：l6_struct.py 的 `if __name__` 里：找一段 500 字左右的文章（就用《教程-Agent运行时.md》第 1 章"讲解"那几段），system 说"你是出题老师，根据文章出选择题"，user 给文章。用 tracked_run 包住 invoke_structured，跑 10 次。每次记录是第几次尝试合格的，或者彻底失败。最后打印统计：第一次合格几次、打回后合格几次、失败几次。

**骨架**：

```python
from llm import chat, MODEL
from runs import init_db, tracked_run
from structured import invoke_structured

ARTICLE = """...500 字..."""
SYSTEM = "你是出题老师。根据用户给的文章出选择题，题目要能考察理解。"


def make_quiz(article: str) -> tuple[Quiz, int]:
    """返回 (结果, 用了几次尝试)。"""
    with tracked_run(agent="l6", model=MODEL) as run:
        quiz = invoke_structured(chat, [
            {"role": "system", "content": SYSTEM},
            {"role": "user", "content": article},
        ], Quiz, check=check_quiz, run=run)
        return quiz, run.seq


if __name__ == "__main__":
    init_db()
    first, retried, failed = 0, 0, 0
    for i in range(10):
        try:
            quiz, tries = make_quiz(ARTICLE)
            ...      # tries == 1 加 first，否则加 retried；打印第几轮、几题、几次尝试
        except RuntimeError as e:
            failed += 1
            print(f"第 {i+1} 轮失败：{e}")
    print(f"一次合格 {first}，打回后合格 {retried}，失败 {failed}")
```

**为什么**：

- `send` 直接传 `chat`：invoke_structured 自己带 tools 和 tool_choice，不需要像 l3 那样包一层。这就是 6.0 给 chat 加参数的原因。
- `return` 写在 with 块里：自检第 1 题说过，return 走 else 分支正常收尾。顺便验证一下你信不信。
- `run.seq` 当"尝试次数"：这个 run 里只有 invoke_structured 的 llm 步，seq 等于试了几次。
- 10 次是为了看分布。模型有随机性，一次成功说明不了什么。

**验证**：打印 10 行加一行统计。然后查表：

```bash
sqlite3 runs.db "select run_id, seq, error from steps where run_id in (select id from runs where agent='l6') and error is not null;"
```

每条 error 就是一次打回的原因。看它们长什么样，这是你第一批"坏样本"。

**常见错误**：

- 400 提到 tool_choice：格式写错，对照 6.0。
- 全部"没有调用工具"：DeepSeek 偶尔这样，看 steps 表 output 里它说了什么，多半是说"好的，我来出题"然后没动。system 里加一句"直接调用工具，不要先回复文字"。
- `ValidationError` 次次都是 answer 类型：模型把 answer 写成 "A" 字符串。Field 描述改得更明确，或者干脆让 answer 用字母，五个 Agent 教程第 4 章 线上版最后就是存标号。
- 10 次花了不少钱：每次 500 字进去几百字出来，10 次大约几分钱。看 runs 表 cost 列加起来。

### 自检

1. 为什么用工具调用做结构化输出，不让模型"输出 JSON"？
   答：自由文本里的 JSON 厂商不保证格式；tool_call 的 arguments 按 schema 约束生成，加 tool_choice 还能强制它必须调。
2. 格式校验和质量校验谁在运行时、谁在 Agent？

3. 打回时忘了回其中一个 tool_call 的 id 会怎样？
   答：下一次请求 400，第 2 章实验二那个错。
4. 三次都不合格为什么抛异常而不是返回 None？
   答：要走 tracked_run 的 except 记 failed；返回 None 调用方容易漏检。
5. steps 表里不合格那几条的 output 有什么用？
   答：改提示词的依据。不看坏样本改提示词是瞎改。

## 第 7 章 变成服务：后台任务与回调

### 先收第 6 章的尾

两件没做完的，开这章之前先做，十分钟：

2. Question 的 answer 改成 `Field(ge=0, le=3, description=...)`，删掉 check_quiz 里 answer 越界那两行。跑一次确认没坏。

### 这一章解决什么问题

到现在都是脚本：`uv run python l6_struct.py`，跑完退出。产品里不是这样。创作者在后台点"生成复习题"，Go 建一条 ai_jobs 记录，POST 给 Python；Python 要跑几十秒，HTTP 请求不能挂着等，所以 Python 立刻回 202"收到了"，后台跑，跑完再 POST 回 Go 说"任务 123 完成，结果是这个"。这叫**异步任务加回调**。

这一章把你的出题变成一个常驻的 HTTP 服务，有四件新东西：

| 东西 | 解决什么 | 线上版里在哪 |
|---|---|---|
| FastAPI 路由加 BackgroundTasks | 收到请求立刻返回，活在后台干 | app/main.py |
| 通用 job_worker | 成功回调 done、失败回调 failed、回调本身失败也兜住 | app/main.py 的 guide_worker 等四个 |
| contextvar 放租户 | 工具查数据要按租户过滤，但租户不能是模型能填的参数 | app/gateway.py 的 current_tenant |
| JSON 日志 | 服务没有 print 给你看，每行一个 JSON 以后能查 | app/log.py |

练习里没有 Go。你写一个假的回调地址 `POST /fake-go/jobs/{id}/complete`，自己调自己，打印收到的东西。以后接真正的 Go 主服务时，把这个假地址换成真的就通了。

### 先看懂做法

**FastAPI 十分钟够用**。它建在 pydantic 上，你第 6 章学的 BaseModel 直接当请求体用：

```python
from fastapi import FastAPI, BackgroundTasks, Header, HTTPException
from pydantic import BaseModel

app = FastAPI()

class JobIn(BaseModel):
    job_id: int
    text: str

@app.post("/agents/quiz/run", status_code=202)
def run_quiz(body: JobIn, background: BackgroundTasks, x_tenant_id: int = Header()):
    ...
    return {"trace_id": trace_id}
```

四个要点：

- `@app.post("/路径")` 把下面的函数注册成路由，和 Express 的 `app.post(path, handler)` 一回事，只是用装饰器写。
- 函数参数怎么来：类型是 BaseModel 的从请求体 JSON 读并校验，`Header()` 的从请求头读（`x_tenant_id` 自动对应 `X-Tenant-Id`），`BackgroundTasks` 由 FastAPI 塞给你。校验不过它自己回 422，你不用写。
- `background.add_task(fn, *args)`：登记一个函数，响应发出去之后在线程池里跑。路由函数返回了，fn 才开始。
- `def` 不是 `async def`：同步路由 FastAPI 会放线程池跑，不会卡住别的请求。你的 chat 是同步 httpx，所以全用 `def`，这章不碰 async。

**worker 的固定形状**。线上版里 guide_worker、index_worker、quiz_worker、graph_worker 四个函数逐行相同，只有中间那一行调的 Agent 不一样。你一开始就写一个通用的：

```
设租户
try:
    结果, run = fn()
    回调 done 带结果和 run_id
except Exception as e:
    try:
        回调 failed 带错误
    except Exception:
        记日志：回调也失败了
```

三层。第一层是 Agent 失败要告诉 Go；第二层是告诉 Go 这件事本身也可能失败（Go 挂了、网络断了），这时只能记日志，Go 那边的任务会一直"进行中"，第 9 章 Go 侧的超时回收就是为这种情况准备的。

**contextvar**。`contextvars.ContextVar` 是一个"当前上下文里的全局变量"：同一个请求里到处能 `get()`，不同请求互不干扰。租户 id 放在这里，入口处 `set`，工具里 `get`，工具的函数签名里没有 `tenant_id` 这个参数，模型想填也没地方填。这就是项目介绍里"越权路径在代码层面不存在"那句话的全部实现。

一个坑：后台任务在线程池里跑，contextvar 不保证自动带过去。所以 worker 第一行要重新 `set`，租户 id 作为普通参数传给 worker。

**JSON 日志**。服务跑在后台，没有终端给你看 print。标准做法是 `logging` 模块加一个每行输出一个 JSON 的 formatter，`log.info("quiz.done", extra={"job_id": 1, "run_id": 5})` 这样打，extra 里的字段进 JSON。以后 `grep trace_id` 就能把一次任务从入口到回调全串起来，和第 4 章 runs 表的 trace_id 是同一个 id。

### 7.1 log.py：每行一个 JSON

**做什么**：新建 `log.py`，一个 `JsonFormatter` 和一个 `setup_logging()`。这是基础设施代码，形状固定，照抄，但要看懂三处注释。

```python
# log.py
import json
import logging
import sys
from datetime import datetime, timezone


class JsonFormatter(logging.Formatter):
    """每行一个 JSON：时间、级别、logger 名、消息，加上 extra 里的字段。"""

    def format(self, record: logging.LogRecord) -> str:
        data = {
            "ts": datetime.now(timezone.utc).isoformat(timespec="milliseconds"),
            "level": record.levelname,
            "logger": record.name,
            "msg": record.getMessage(),
        }
        # 注释一：log.info("...", extra={"a": 1}) 里的字段会挂在 record 上，挑出来
        for k, v in record.__dict__.items():
            if k not in _STD_FIELDS and not k.startswith("_"):
                data[k] = v
        # 注释二：log.exception(...) 会带异常栈，放进 exc 字段
        if record.exc_info:
            data["exc"] = self.formatException(record.exc_info)
        return json.dumps(data, ensure_ascii=False, default=str)


# 注释三：LogRecord 自带的字段名集合，用一个空 record 算出来，剩下的就是 extra 里的
_STD_FIELDS = set(logging.LogRecord("", 0, "", 0, "", (), None).__dict__) | {"message", "asctime", "color_message"}


def setup_logging(level: str = "INFO") -> None:
    handler = logging.StreamHandler(sys.stdout)
    handler.setFormatter(JsonFormatter())
    root = logging.getLogger()
    root.handlers.clear()
    root.addHandler(handler)
    root.setLevel(level)
    # uvicorn 自带 handler，清掉让它走 root 的 JSON 格式
    for name in ("uvicorn", "uvicorn.access", "uvicorn.error"):
        lg = logging.getLogger(name)
        lg.handlers.clear()
        lg.propagate = True
    # httpx 每个请求都打一行 INFO，太吵
    for name in ("httpx", "httpcore"):
        logging.getLogger(name).setLevel(logging.WARNING)
```

**为什么**：

- 为什么不用 print：print 没有级别、没有时间、没有结构。logging 的 `extra` 让你把 job_id、trace_id 当字段打，而不是拼进字符串里再用正则抠。
- `log.exception` 和 `log.error` 的区别：exception 只能在 except 块里用，自动带上异常栈。worker 里失败用它。
- `default=str`：extra 里万一塞了 Decimal 或 datetime，json.dumps 不认识，用 str 兜底，和第 4 章 add_step 里一样。

**验证**：

```bash
uv run python -c "

from log import setup_logging
setup_logging()
log = logging.getLogger('demo')
log.info('hello', extra={'job_id': 1, 'trace_id': 'abc'})
try:
    1/0
except Exception:
    log.exception('boom', extra={'job_id': 1})
"
```

两行 JSON，第一行有 job_id 和 trace_id 字段，第二行有 exc 字段带 ZeroDivisionError 的栈。

### 7.2 main.py：骨架、鉴权、假 Go

**做什么**：新建 `main.py`，先只做三个路由：健康检查、假 Go、以及一个 `require_internal` 函数。先不碰出题，把服务跑起来。

**骨架**：

```python
# main.py
import hmac
import logging
import os

from dotenv import load_dotenv
from fastapi import FastAPI, BackgroundTasks, Header, HTTPException
from pydantic import BaseModel

from log import setup_logging
from runs import init_db, new_trace_id

load_dotenv()
setup_logging()
log = logging.getLogger("agent-runtime")

INTERNAL_TOKEN = os.environ["INTERNAL_TOKEN"]

app = FastAPI(title="agent-runtime")
init_db()


@app.get("/health")
def health():
    return {"ok": True}


def require_internal(token: str) -> None:
    """内部接口鉴权：只认共享密钥。"""
    if not hmac.compare_digest(token, INTERNAL_TOKEN):
        raise HTTPException(status_code=401, detail="bad internal token")


class CompleteIn(BaseModel):
    status: str
    result: dict | None = None
    run_id: int = 0
    error: str = ""


@app.post("/fake-go/jobs/{job_id}/complete")
def fake_go_complete(job_id: int, body: CompleteIn, x_tenant_id: int = Header(), x_trace_id: str = Header()):
    """假装自己是 Go：把回调收到的东西打进日志。"""
    log.info("fake_go.complete", extra={...})     # job_id、tenant_id、trace_id、status、run_id、error，
                                                   # result 只记题数不记全文，太长
    return {"ok": True}
```

**为什么**：

- `hmac.compare_digest` 而不是 `==`：常量时间比较，防止靠响应时间猜密钥。鉴权代码一律用它，养成习惯。
- `require_internal` 是普通函数不是装饰器：路由里显式调一行 `require_internal(x_internal_token)`，看得见。FastAPI 有 Depends 机制可以做得更漂亮，第 10 章再说。
- 假 Go 的 result 只记题数：日志每行一个 JSON，塞整份 quiz 进去几 KB，查日志时满屏都是题。记"够定位问题"的字段，全文在 steps 表里。
- `init_db()` 在模块顶层：服务启动建表，和脚本里放 `if __name__` 下面不同，因为 uvicorn 是 import 这个文件，不会跑 `if __name__`。

### 7.3 gateway.py：租户与回调

**做什么**：新建 `gateway.py`，一个 contextvar 和一个 `complete_job`。

**骨架**：

```python
# gateway.py
import os
from contextvars import ContextVar

import httpx
from dotenv import load_dotenv

load_dotenv()

# 当前请求的租户，由入口处设置，工具里只读。模型永远碰不到它。
current_tenant: ContextVar[int] = ContextVar("current_tenant")

_client = httpx.Client(
    base_url=os.environ["API_BASE_URL"],
    headers={"X-Internal-Token": os.environ["INTERNAL_TOKEN"]},
    timeout=10,
    trust_env=False,
)


def complete_job(job_id: int, *, status: str, trace_id: str,
                 result: dict | None = None, run_id: int = 0, error: str = "") -> None:
    """把任务结果回写给 Go。status 是 done 或 failed。"""
    resp = _client.post(
        f"/fake-go/jobs/{job_id}/complete",
        json={...},                                    # 四个字段，对着 7.2 的 CompleteIn 填
        headers={"X-Tenant-Id": str(current_tenant.get()), "X-Trace-Id": trace_id},
    )
    resp.raise_for_status()
```

**为什么**：

- `current_tenant.get()` 没 set 过会抛 LookupError。这是故意的：忘了设租户就该炸，不能默默用一个默认值查到别人的数据。
- 租户走请求头不走 body：和 Go 那边 `middleware.Internal` 的约定一致，它从 `X-Tenant-Id` 读。Go 主服务的中间件就是从这个头读租户的。
- `_client` 模块级一个，和 llm.py 一样复用连接。前缀下划线表示"模块内部用，别 import 它"。
- `raise_for_status()`：回调失败要抛出来，worker 的第二层 try 才接得住。

**验证**：先在 `-c` 里体会 contextvar：

```bash

    current_tenant.get()
except LookupError as e:
    print('没 set 就 get：', repr(e))
current_tenant.set(7)
print('set 之后：', current_tenant.get())
"
```

### 7.4 job_worker 与 /agents/quiz/run

**做什么**：先给 l6_struct.py 的 make_quiz 动两刀，再在 main.py 加通用 worker 和出题路由。

**l6_struct.py 改两处**：

```python
def make_quiz(article: str, *, trace_id: str | None = None) -> tuple[Quiz, Run]:
    """返回 (结果, 这次的 Run)。调用方从 Run 上拿 id 或 seq。"""
    if not article.strip():
        raise ValueError("文章为空")
    with tracked_run(trace_id=trace_id, agent="quiz", model=MODEL) as run:
        quiz = invoke_structured(chat, [...], Quiz, check=check_quiz, run=run)
        return quiz, run
```

`if __name__` 里原来的 `quiz, tries = make_quiz(ARTICLE)` 改成 `quiz, run = make_quiz(ARTICLE)`，`tries` 用 `run.seq`。`Run` 要从 runs import。agent 名从 "l6" 改成 "quiz"，它现在是产品代码不是练习了。

**为什么**：返回 Run 对象而不是 run.id，调用方要什么自己取，脚本要 seq，服务要 id，函数不用为两边各写一个版本。with 块结束后 Run 对象还在，id、seq、token 都在上面。空文章提前抛，而且抛在 with 外面：这不是 Agent 执行失败，是输入不合法，不该占一条 run 记录。

**main.py 追加**：

```python
from typing import Callable
import gateway
from l6_struct import make_quiz


def job_worker(agent_name: str, fn: Callable, job_id: int, tenant_id: int, trace_id: str) -> None:
    """通用后台 worker：设租户，跑 fn，成功失败都回调。fn 无参，返回 (pydantic 结果, Run)。"""
    gateway.current_tenant.set(tenant_id)
    try:
        result, run = fn()
        gateway.complete_job(job_id, status="done", trace_id=trace_id, result=result.model_dump(), run_id=run.id)
        log.info(f"{agent_name}.done", extra={"job_id": job_id, "run_id": run.id, "trace_id": trace_id})
    except Exception as e:
        log.exception(f"{agent_name}.failed", extra={"job_id": job_id, "trace_id": trace_id})
        try:
            ...                                         # 回调 failed，error 用 repr(e)[:500]
        except Exception:
            log.exception(f"{agent_name}.callback_failed", extra={"job_id": job_id, "trace_id": trace_id})


class QuizRunIn(BaseModel):
    job_id: int
    text: str


@app.post("/agents/quiz/run", status_code=202)
def run_quiz(body: QuizRunIn, background: BackgroundTasks,
             x_internal_token: str = Header(), x_tenant_id: int = Header(),
             x_trace_id: str | None = Header(default=None)):
    require_internal(x_internal_token)
    trace_id = x_trace_id or new_trace_id()
    background.add_task(job_worker, "quiz", lambda: make_quiz(body.text, trace_id=trace_id),
                        body.job_id, x_tenant_id, trace_id)
    log.info("quiz.accepted", extra={"job_id": body.job_id, "tenant_id": x_tenant_id, "trace_id": trace_id})
    return {"trace_id": trace_id}
```

**为什么**：

- `fn` 是一个无参函数，路由用 `lambda:` 把 text 和 trace_id 包进去。lambda 就是 JS 的箭头函数 `() => make_quiz(body.text, trace_id)`。这样 job_worker 不知道出题要什么参数，下一个 Agent 换个 lambda 就能复用。
- 为什么 worker 第一行 set 租户：后台任务在线程池里跑，路由函数里 set 的 contextvar 不保证带过去。租户作为普通参数传进来再 set 一次，稳。
- `error=repr(e)[:500]`：回调给 Go 的错误要截断，Go 那边是数据库字段，不能无限长。全文在日志的 exc 字段和 runs 表的 error 列。
- trace_id 优先用请求头的：Go 生成后传过来，Python 记进 runs 表和每行日志。练习里 curl 不传，自己生成。第 4 章说过的"一个 id 两边都能查"在这里闭环。
- `status_code=202`：Accepted，意思是"收到，还没做完"。200 会让调用方以为结果在响应里。
- 日志打 `quiz.accepted`：请求进来一行、完成一行、回调收到一行，三行同一个 trace_id。

**验证**：服务开着（`--reload` 会自动重启），把文章存成文件再发，省得在命令行里贴长文：

**常见错误**：

- 启动报 `KeyError: 'INTERNAL_TOKEN'`：.env 没加，或者 main.py 里 `load_dotenv()` 写在 `os.environ[...]` 后面。
- 回调时 `LookupError` 没有 current_tenant：worker 第一行忘了 set。
- 空文章那次 runs 表多了一条 failed：ValueError 抛在了 with 里面。按 7.4 的骨架抛在 with 外面。
- curl 发了没反应、uvicorn 也没日志：服务没起来，或者端口不是 8000。先 `curl localhost:8000/health`。

### 自检

1. 为什么不让请求挂着等结果？
   答：出题要几十秒，HTTP 连接挂几十秒会被网关、浏览器、负载均衡各种超时切断；而且调用方的线程被占着。先回 202，结果靠回调送回去。
2. 租户 id 为什么不能是工具参数？
   答：工具参数是模型填的。模型能填就能填错、能被提示词注入诱导填别人的。放 contextvar 里，工具签名没有这个参数，模型没有任何途径碰到它。
3. worker 里回调本身失败了怎么办？任务会处于什么状态？
   答：只能记日志，Python 这边 runs 表是 done，Go 那边任务永远"进行中"。Python 修不了这个，要 Go 侧对超时未回调的任务做回收，第 9 章讲。
4. 为什么 worker 要通用而不是每个 Agent 一个？
   答：四个 worker 逐行相同，只有调 Agent 那行不同。抄四份，改一处漏三处，线上版就是这么来的。
5. 服务被 kill 时正在跑的后台任务去哪了？
   答：丢了。BackgroundTasks 是进程内的，没有持久化。runs 表留一条 running，Go 那边一条进行中。第 9 章的卡住回收兜 Python 这边，Go 侧回收兜 Go 那边。

## 第 8 章 流式：SSE 与事件协议

### 这一章解决什么问题

第 7 章的出题是创作者点一下、几十秒后回表，没人盯着等。问答不一样：读者打了问题在屏幕前等，要边生成边显示，第一个字越早出来越好。第 1 章 1.4 你已经用 `"stream": True` 拿到一片片文字并打印，这章是把那些片转发给前端。

三件新东西：

| 东西 | 解决什么 | 线上版里在哪 |
|---|---|---|
| SSE 格式和事件协议 | 前端怎么知道这一片是正文、是开头、还是结束 | app/main.py 的 sse()，tutor 的 meta / delta / done / error |
| 生成器加 StreamingResponse | 同步的流怎么挂到 FastAPI 上一片片发 | app/main.py 的 tutor_stream |
| GeneratorExit 收尾 | 读者中途关页面，run 不能永远 running | tutor/agent.py 的 except GeneratorExit |

还有一个流式特有的难点：token 用量在最后一片才给，记账要等流结束；读者中途走了，用量就没有了。

### 先看懂做法

**SSE 是什么**。Server-Sent Events，HTTP 长连接上一行行发文本的约定。一个事件三行：

```
event: delta
data: {"text": "租户"}
(空行)
```

`event:` 是事件名，`data:` 是内容，空行表示这个事件完了。浏览器的 `EventSource` 和 fetch 流都认这个格式。前端你熟，服务端就是把字典变成这三行字符串，`media_type="text/event-stream"`。

**事件协议先定，前端不猜**。线上版定了四种，你照用：

| 事件 | 什么时候 | 带什么 |
|---|---|---|
| meta | 开头一次 | run_id，以后还有 mode |
| delta | 文字片段，多次 | text |
| done | 正常结束一次 | input_tokens、output_tokens，以后还有引用 |
| error | 出错时代替 done | message，可直接展示给读者 |

前端收到 meta 开始渲染，收到 delta 往后拼，收到 done 或 error 关连接。被拒答的问题也走 meta、delta、done，前端不用特殊处理。

**生成器**。第 5 章你写过带 yield 的函数，那是给 with 用的。这章的 `answer_stream` 也是带 yield 的函数，但是当"一片片产出事件"用：每 yield 一个字典，调用方就拿到一个事件。Python 里这叫生成器，JS 的 `function*` 同一回事。生成器的特点是**惰性**：没人调 `next()` 它就停在上一个 yield 不动。这个特点是这章最大的坑的来源。

**读者关页面时发生什么**。FastAPI 从生成器取一片、发一片。读者断开，FastAPI 不再取，生成器停在某个 yield 上。它没结束、没报错，只是没人推了。`with tracked_run` 还没退出，finish_run 没调，run 永远 running。模型那边的流也开着，字还在生成，钱还在花。

解法两步：服务端那层在 `finally` 里调 `gen.close()`；`close()` 会在生成器停着的那个 yield 处抛一个 `GeneratorExit`，生成器用 `except GeneratorExit` 接住，把 `run.status` 改成 aborted，然后退出。这是第 5 章 run.status 为什么设计成可改的原因，到这章才用上。

一个细节：`GeneratorExit` 不是 `Exception` 的子类，`except Exception` 接不到它，tracked_run 的 except 分支也接不到。所以要单独写，而且接住后用 `return` 退出 with 块，让 tracked_run 走 else 分支把 aborted 写进表。

### 8.0 没有新依赖

这章不装东西。FastAPI 的 `StreamingResponse` 和 Starlette 的 `iterate_in_threadpool` 第 7 章装 fastapi 时已经有了。

### 8.1 llm.py：chat_stream

**做什么**：llm.py 追加 `chat_stream(messages) -> Iterator[dict]`，第 1 章 1.4 那段的生产版。逐片 yield `{"text": 片段}`，最后一片 yield `{"text": "", "usage": {...}}`。

**骨架**：

```python
from typing import Iterator


def chat_stream(messages: list[dict]) -> Iterator[dict]:
    """流式发一次请求，逐片产出 {"text": ...}；最后一片是 {"text": "", "usage": {...}}。"""
    body = {"model": MODEL, "messages": messages, "stream": True,
            "stream_options": {"include_usage": True}}
    with client.stream("POST", "/chat/completions", headers=HEADERS, json=body) as resp:
        resp.raise_for_status()
        for line in resp.iter_lines():
            if not line.startswith("data: "):
                continue
            payload = line[len("data: "):]
            if payload == "[DONE]":
                break
            chunk = json.loads(payload)
            if chunk.get("usage"):
                yield {"text": "", "usage": chunk["usage"]}
                continue
            ...                                        # 取 choices[0].delta.content，有内容才 yield {"text": ...}
```

**为什么**：

- `stream_options: {"include_usage": true}`：不加这个，流式返回里没有 usage，记账无从谈起。加了之后最后多一片，choices 为空、只有 usage。
- usage 那片 `choices` 是空列表，所以要先判 usage 再取 choices[0]，顺序反了会 IndexError。
- 为什么放 llm.py 不放 stream.py：它和 chat 用同一个 client、同一个 HEADERS，是模型客户端层的事。第 10 章换 LangChain 时它们一起换。
- 返回 Iterator[dict] 而不是直接 print：第 1 章讲过，循环里只收片，判断留给调用方。

**验证**：

```bash
uv run python -c "
from llm import chat_stream
for p in chat_stream([{'role': 'user', 'content': '用两句话介绍 RAG'}]):
    print(repr(p))
"
```

一行一个字典，最后一行有 usage，prompt_tokens 和 completion_tokens 都不为零。

### 8.2 stream.py：answer_stream

**做什么**：新建 `stream.py`，写 `answer_stream(question, *, trace_id=None) -> Iterator[dict]`。yield meta、若干 delta、done；读者断开时记 aborted。

**骨架**：

```python
# stream.py
import time
from typing import Iterator

from llm import chat_stream, MODEL
from runs import tracked_run

SYSTEM = "你是读者的学习助教，用中文简洁回答。"


def answer_stream(question: str, *, trace_id: str | None = None) -> Iterator[dict]:
    """逐事件产出 meta → delta* → done。读者断开时收到 GeneratorExit，记 aborted。"""
    with tracked_run(trace_id=trace_id, agent="tutor", model=MODEL) as run:
        messages = [{"role": "system", "content": SYSTEM}, {"role": "user", "content": question}]
        full, usage = "", {}
        t1 = time.perf_counter()
        try:
            yield {"event": "meta", "run_id": run.id}
            for piece in chat_stream(messages):
                if piece.get("usage"):
                    usage = run.add_usage(piece["usage"])
                    continue
                full += piece["text"]
                yield {"event": "delta", "text": piece["text"]}
        except GeneratorExit:
            run.status = "aborted"
            run.step("llm", run.model, input=messages, output={"content": full, "partial": True},
                     latency_ms=int((time.perf_counter() - t1) * 1000), error="client disconnected")
            return
        run.step(...)                                   # 和第 6 章一样：input 是 messages，output 存整段 full，带 usage 和 latency
        yield {"event": "done", "input_tokens": usage.get("prompt_tokens", 0),
               "output_tokens": usage.get("completion_tokens", 0)}
```

**为什么**：

- `except GeneratorExit` 里是 `return` 不是 `raise`：return 让 with 块正常结束，tracked_run 走 else 分支，用 `run.status`（已经是 aborted）写表。raise 的话 GeneratorExit 会穿过 tracked_run，它的 `except Exception` 接不到，finish_run 根本不会被调，表里还是 running。教程里写的"再 raise"在你这个 tracked_run 的实现下行不通，这是教程和你代码对不上的地方，以你跑出来的结果为准。
- aborted 时也记一条 step：output 存已经收到的半截 full，error 写明原因。这样查表时能看到读者走的时候模型说到哪了。token 没有，因为 usage 在最后一片，没收到。这是流式记账的硬伤，只能接受。
- `return` 之后 for 循环没跑完，`chat_stream` 那个生成器被丢弃，Python 会自动关掉它，`with client.stream` 退出，连接断开，模型那边停止生成。不用你手动管，但要知道这一步发生了。
- meta 在 try 里面：第一个 yield 就可能遇到断开。
- 不检查空问题：那是路由的事，8.3 里用 400 挡。

**验证**：先不经过 HTTP，直接在 `-c` 里跑两种情况：

```bash
uv run python -c "

from stream import answer_stream
init_db()

print(evs[0], evs[-1], sep='\n')
rid = evs[0]['run_id']
print('status:', get_run(rid)['status'])
# 情况二：取两片就 close，模拟读者断开

print(next(gen)); print(next(gen))
gen.close()
print('status:', get_run(rid + 1)['status'])
"
```

情况一打出 meta 和 done，status 是 done，done 里的 token 不为零。情况二打出 meta 和一片 delta，status 是 aborted。第二个 status 如果是 running，回头看 except GeneratorExit 是不是用了 raise。

### 8.3 main.py：sse 和流式路由

**做什么**：main.py 追加 `sse()` 和 `POST /agents/tutor/stream`。

**骨架**：

```python
import json
from fastapi.responses import StreamingResponse
from starlette.concurrency import iterate_in_threadpool
from stream import answer_stream


def sse(ev: dict) -> str:
    """一个事件字典 → 一段 SSE 文本：event 行 + data 行 + 空行。"""
    name = ev.get("event", "message")
    data = {k: v for k, v in ev.items() if k != "event"}
    return ...                                           # f-string 拼三行，data 用 json.dumps(ensure_ascii=False)


class AskIn(BaseModel):
    question: str


@app.post("/agents/tutor/stream")
def tutor_stream(body: AskIn, x_internal_token: str = Header(), x_tenant_id: int = Header(),
                 x_trace_id: str | None = Header(default=None)):
    require_internal(x_internal_token)
    q = body.question.strip()
    if not q or len(q) > 500:
        raise HTTPException(status_code=400, detail="question must be 1-500 chars")
    trace_id = x_trace_id or new_trace_id()
    gateway.current_tenant.set(x_tenant_id)
    gen = answer_stream(q, trace_id=trace_id)

    async def events():
        try:
            async for ev in iterate_in_threadpool(gen):
                yield sse(ev)
        finally:
            gen.close()

    log.info("tutor.stream", extra={"tenant_id": x_tenant_id, "trace_id": trace_id})
    return StreamingResponse(events(), media_type="text/event-stream",
                             headers={"Cache-Control": "no-cache", "X-Accel-Buffering": "no"})
```

**为什么**：

- `events()` 是 `async def` 加 `yield`，异步生成器。这是全教程唯一一处 async，原因是 StreamingResponse 要在事件循环里一片片发，而你的 answer_stream 是同步的、里面有阻塞的网络读。`iterate_in_threadpool` 把同步生成器放到线程池里取，每取一片回到事件循环发一片。
- `finally: gen.close()`：读者断开时 Starlette 取消的是 `events()` 这个协程，finally 一定跑。正常结束时 close 是空操作；断开时它触发 8.2 的 GeneratorExit。没有这行，就是"先看懂做法"里说的永远 running。
- `X-Accel-Buffering: no`：nginx 默认攒够一块才转发，流式会变成一次吐。本地没 nginx 看不出差别，上线必踩，现在就带上。
- `Cache-Control: no-cache`：流不能被缓存。
- 租户在路由里 set：这章没有工具要查租户，但约定不变，入口 set。
- 空问题和超长问题在路由层 400：这是输入不合法，和第 7 章空文章同一个道理，不该占 run。

**验证**：服务开着，`-N` 让 curl 不缓冲：

```bash
curl -N -X POST localhost:8000/agents/tutor/stream -H "X-Internal-Token: dev" -H "X-Tenant-Id: 1" \
  -H "Content-Type: application/json" -d '{"question": "用三句话介绍 RAG"}'
```

应该看到事件一组组冒出来，先 meta，然后一串 delta，最后 done。不是等几秒一次全出。

然后模拟读者断开：再发一次，看到前几个 delta 就 **Ctrl+C**。查表：

```bash
sqlite3 runs.db "select id, agent, status, error from runs where agent='tutor' order by id desc limit 2;"
```

两条：先完成的那条 done，被你掐断的那条 aborted。如果是 running，看 finally 有没有 close，以及 8.2 验证情况二过没过。

**常见错误**：

- curl 等很久一次全出：少了 `-N`，是 curl 在攒，不是服务端。
- `TypeError: Object of type ... is not JSON serializable`：sse 里 json.dumps 碰到了不能序列化的东西，看 ev 里放了什么。
- Ctrl+C 后表里是 running：三种可能，finally 没写、except GeneratorExit 用了 raise、或者你掐得太早在 meta 之前连接还没建立。多等一两片再掐。
- 断开后 uvicorn 日志有一行 "generator already executing"：掐的瞬间生成器正在线程池里收网络包，close 撞上了。多发生在网络慢的时候，重试一次即可；线上版线上也偶尔有，不算 bug。

### 8.4 进阶：攒头判标签

**做什么**：让模型第一行输出 `[简短]` 或 `[详细]` 标签，answer_stream 把标签判出来放进 meta 的 mode，delta 里不含标签。

system 改成：

```python
SYSTEM = "你是读者的学习助教，用中文回答。第一行只写 [简短] 或 [详细] 表示你打算怎么答，换行后再写正文。"
```

**骨架**，替换 8.2 里 for 循环那段：

```python
MODE_TAGS = {"[简短]": "brief", "[详细]": "detailed"}

def split_mode(text: str) -> tuple[str, str]:
    """第一行是标签，返回 (mode, 去掉标签的正文)。没标签按 brief。"""
    first, _, rest = text.partition("\n")
    for tag, mode in MODE_TAGS.items():
        if first.strip().startswith(tag):
            return mode, ...                             # 第一行去掉标签剩下的 + 换行 + rest，再 strip
    return "brief", text

# answer_stream 里：
head, mode = "", None
for piece in chat_stream(messages):
    if piece.get("usage"):
        usage = run.add_usage(piece["usage"]); continue
    text = piece["text"]
    full += text
    if mode is None:
        head += text
        if "\n" not in head and len(head) < 12:
            continue                                     # 标签最长 4 个字，12 字内必见换行
        mode, rest = split_mode(head)
        yield {"event": "meta", "run_id": run.id, "mode": mode}
        if rest:
            yield {"event": "delta", "text": rest}
    else:
        yield {"event": "delta", "text": text}
if mode is None:                                         # 回答极短，整段都没到 12 字
    mode, rest = split_mode(head)
    yield {"event": "meta", "run_id": run.id, "mode": mode}
    if rest:
        yield {"event": "delta", "text": rest}
```

meta 不再是第一个 yield，它要等看清标签。

**为什么**：

- 标签会被拆成几片：`"[简"`、`"短]"`、`"\n正文"`。所以不能看第一片，要攒到见换行。12 字是上限兜底，防止模型不换行把整段都攒住。
- 攒头是运行时的事，标签含义是 Agent 的事。MODE_TAGS 和 split_mode 属于 Agent，攒头那个 if 属于运行时。线上版的 tutor 还没把这两层拆开，五个 Agent 教程第 3 章会让你拆。
- 落库的 full 含标签，发给前端的 delta 不含。表里存原始输出，是第 6 章说的坏样本原则。

**验证**：curl 两个问题，一个"RAG 是什么"，一个"详细讲讲 RAG 的检索和生成两步各做什么"。meta 的 mode 应该一个 brief 一个 detailed，delta 的第一片不含方括号。查 steps 表 output 里的 content 是带标签的原文。

### 自检

1. 为什么 token 要等到流结束才有？对记账意味着什么？
   答：厂商在最后一片才给 usage。所以 finish_run 必须等流结束；读者中途断开，usage 收不到，那条 run 的 token 只能记 0，钱花了但记不到账。流式记账天然有这个缺口。
2. 读者关页面后服务端发生了什么？不处理会留下什么？
   答：FastAPI 不再从生成器取片，生成器停在某个 yield 上。不处理：run 永远 running，模型的流还开着继续生成继续花钱。处理：服务端 finally 里 gen.close()，生成器 except GeneratorExit 记 aborted 并退出，退出时模型连接随之关闭。
3. 为什么被拒答也要发 meta、delta、done？
   答：前端只认一套协议。拒答走同一套，前端不用写"如果是拒答就怎样"的分支，拒答文案就是一条 delta。
4. 为什么 except GeneratorExit 里用 return 不用 raise？
   答：GeneratorExit 不是 Exception，tracked_run 的 except 接不到；raise 的话 finish_run 不会被调。return 让 with 正常退出走 else 分支，用改过的 run.status 写表。
5. events() 为什么是 async 的，而别处都是 def？
   答：StreamingResponse 要在事件循环里一片片发。answer_stream 是同步的，iterate_in_threadpool 把它放线程池，每片回到事件循环发出去。这是同步代码和异步框架之间唯一要搭的桥。

## 第 9 章 稳：超时、熔断、卡住回收

### 这一章解决什么问题

前八章的代码在厂商正常时都对。厂商抖一下，三件事会露出来：

| 问题 | 现象 | 这章的对策 |
|---|---|---|
| 请求挂死 | 一个不返回的请求占住线程几分钟 | 超时：后台 60 秒，问答 20 秒 |
| 厂商整体故障 | 每个读者都等满 20 秒才失败，线程池被占满拖垮别的接口 | 熔断器：连续失败到阈值就直接拒绝，冷却后放一个试探 |
| 进程被杀 | run 永远 running，成本算不进去，创作者看到永远进行中 | 卡住回收：每 5 分钟把超过 30 分钟的 running 标成 failed |

前几章实验留下的 running 记录（进程被杀、异常没接住）就是第三种，这章拿它们当测试数据；一条都没有也不要紧，9.5 会手工插一条。

这章还第一次写**单元测试**。熔断器是个状态机，靠 curl 验不了"连续失败三次后第四次立刻拒绝、30 秒后放一个"，要用假时钟在代码里拨。

### 先看懂做法

**超时**。httpx 的 Client 建的时候给了 `timeout=60`，这是全局的。问答读者在等，20 秒不回就该放弃，所以 chat_stream 要能单独指定。httpx 每次请求可以覆盖：`client.stream(..., timeout=20)`。超时值放 .env。

**熔断器是个三态状态机**：

```
         连续失败 fail_max 次              冷却 cooldown 秒
closed ─────────────────────▶ open ─────────────────────▶ half_open
  ▲                            ▲                              │
  │        试探成功             │          试探失败             │
  └────────────────────────────┴──────────────────────────────┘
```

- closed：正常放行，记连续失败次数，成功一次清零。
- open：直接抛 CircuitOpen，请求根本不发。读者立刻看到"小课暂时休息"。
- half_open：只放**一个**试探请求，其他的照样拒。试探成功回 closed，失败再 open 一轮。

实现就是一个类：`before()` 在请求前查状态并决定放不放，`success()` 和 `failure()` 在请求后更新。状态不用单独存一个变量，用"什么时候打开的"算出来：`_opened_at` 是 None 就是 closed，距今不到 cooldown 是 open，超过了是 half_open。多线程同时调要加锁，第 7 章的后台任务和第 8 章的流都在线程池里。

**流式的判定不一样**。普通调用成功失败一目了然。流式的"成功"是拿到第一片：说明连上了、厂商在吐字。之后读者中途断开是读者的事，不算依赖失败，不能记进熔断计数。

**卡住回收**。一条 SQL：`UPDATE runs SET status='failed', error=... WHERE status='running' AND created_at < 30 分钟前`。放一个后台协程里每 5 分钟跑一次。30 分钟怎么定：最长的正常执行也就几分钟，留十倍余量。线上版排除了裁判（评测一跑几十分钟），你现在没有裁判，不用排。

**熔断和重试的关系**。偶发错误重试，持续错误熔断。重试在熔断之内：熔断器包在最外面，里面可以重试几次，几次都失败才算熔断器的一次失败。这章不加重试，第 10 章 LangChain 的 max_retries 会碰到。

### 9.1 超时：llm.py 读配置

**做什么**：llm.py 的 client 超时改成读 .env，chat_stream 加 `timeout` 参数。

```python
LLM_TIMEOUT = float(os.environ.get("LLM_TIMEOUT", 60))
TUTOR_TIMEOUT = float(os.environ.get("TUTOR_TIMEOUT", 20))

client = httpx.Client(base_url=BASE_URL, timeout=LLM_TIMEOUT, trust_env=False)


def chat_stream(messages: list[dict], *, timeout: float = TUTOR_TIMEOUT) -> Iterator[dict]:
    ...
    with client.stream("POST", "/chat/completions", headers=HEADERS, json=body, timeout=timeout) as resp:
```

**为什么**：

- `os.environ.get(名字, 默认值)` 而不是 `os.environ[名字]`：超时没配就用默认，不该让服务起不来。密钥和地址用 `[]`，没配就该炸，两种写法对应两种配置。
- 流式的 timeout 是**每次读**的超时，不是整个流的。20 秒内一个字都没来才算超时，正常吐字时每片间隔不到一秒。
- 问答超时短是因为读者在等；后台任务没人等，宁可慢也别失败。

**验证**：不好验，超时要厂商真的不回。放到 9.6 一起看。

### 9.2 breaker.py：三态状态机

**做什么**：新建 `breaker.py`，`CircuitOpen` 异常和 `Breaker` 类。

**骨架**：

```python
# breaker.py
import logging
import os
import threading
import time
from collections.abc import Callable, Iterator

log = logging.getLogger(__name__)


class CircuitOpen(Exception):
    """熔断中，请求没有发出去。"""


class Breaker:
    def __init__(self, name: str, fail_max: int, cooldown: float, clock: Callable[[], float] = time.monotonic):
        self.name = name
        self.fail_max = fail_max
        self.cooldown = cooldown
        self._clock = clock
        self._lock = threading.Lock()
        self._fails = 0
        self._opened_at: float | None = None
        self._probing = False

    @property
    def state(self) -> str:
        with self._lock:
            return self._state()

    def _state(self) -> str:
        """closed / open / half_open，从 _opened_at 和时钟算出来，不单独存。调用方必须已持锁。"""
        if self._opened_at is None:
            return "closed"
        ...                                                # 距打开不到 cooldown 是 open，否则 half_open

    def before(self) -> None:
        """请求前调用：熔断中就抛 CircuitOpen；半开时只放第一个试探。"""
        with self._lock:
            st = self._state()
            if st == "open" or (st == "half_open" and self._probing):
                raise CircuitOpen(f"{self.name} circuit open")
            if st == "half_open":
                self._probing = True

    def success(self) -> None:
        with self._lock:
            if self._opened_at is not None:
                log.info("breaker.closed", extra={"breaker": self.name})
            self._fails, self._opened_at, self._probing = 0, None, False

    def failure(self) -> None:
        with self._lock:
            self._fails += 1
            self._probing = False
            if ...:                                        # 已经打开过（试探失败）或者连续失败到了阈值
                self._opened_at = self._clock()
                log.warning("breaker.open", extra={"breaker": self.name, "fails": self._fails})

    def call(self, fn: Callable):
        """包一次普通调用。"""
        self.before()
        try:
            out = fn()
        except Exception:
            self.failure()
            raise
        self.success()
        return out

    def stream(self, it: Iterator) -> Iterator:
        """包一个流：拿到第一片才算成功；第一片之前出错算失败；中途断开不算依赖失败。"""
        self.before()
        first = True
        try:
            for x in it:
                if first:
                    self.success()
                    first = False
                yield x
        except GeneratorExit:
            raise
        except Exception:
            if first:
                self.failure()
            raise
        if first:                                          # 流是空的也算连通
            self.success()


def _env(name: str, default: float) -> float:
    return float(os.environ.get(name, default))


# 进程内单例，每个依赖一个。多进程部署时各进程独立计数，够用。
llm_breaker = Breaker("llm", fail_max=int(_env("BREAKER_FAIL_MAX", 3)), cooldown=_env("BREAKER_COOLDOWN", 30))
```

**为什么**：

- `clock` 可注入：默认 `time.monotonic`，测试时换成一个能手动拨的假时钟，不用真等 30 秒。这是"依赖注入"最小的例子，以后看到 LangChain、harness 里到处是这个套路。
- `_state` 不加锁、`state` 加锁：内部方法假设调用方已持锁，对外属性自己加锁。两个都加锁会死锁，threading.Lock 不可重入。
- `_probing` 标记：半开时第一个 before 把它设 True，后面的 before 看到 True 就拒。试探的 success 或 failure 都把它清掉。
- failure 里"已经打开过"那个条件：试探失败时 `_fails` 可能只有 1，没到阈值，但 `_opened_at` 不是 None，也要重新打开。两个条件缺一不可，9.3 的第三个测试专门测它。
- `stream` 里 `except GeneratorExit: raise` 写在 `except Exception` 前面：GeneratorExit 不是 Exception，这行其实多余，但写出来是为了让读的人知道断开不算失败是有意的。
- `call` 里 except 后 `raise`：熔断器只计数，不吞错。和 tracked_run 一个道理。

**验证**：9.3 的测试。

### 9.4 接入：chat、chat_stream、answer_stream

**做什么**：三处改。

**llm.py**：chat 用 `call` 包，chat_stream 用 `stream` 包。chat_stream 原来的函数体改名成 `_chat_stream_raw`，新的 chat_stream 只有一行：

```python
from breaker import llm_breaker


def chat(messages, tools=None, tool_choice=None) -> dict:
    ...
    return llm_breaker.call(lambda: _post(body))           # 把原来 post 到 return 那三行抽成 _post

```

`yield from` 是"把另一个生成器的东西原样转发"，JS 的 `yield*`。

**stream.py**：熔断中要立刻给读者一个 error 事件，而不是让 CircuitOpen 穿出去把连接掐断。把 `with tracked_run` 整个包进 try：

```python
from breaker import CircuitOpen

BUSY_TEXT = "小课暂时休息一下，请稍后再试"


def answer_stream(question: str, *, trace_id: str | None = None) -> Iterator[dict]:
    try:
        with tracked_run(trace_id=trace_id, agent="tutor", model=MODEL) as run:
            ...                                            # 原来的全部内容，不动
    except CircuitOpen:
        yield {"event": "error", "message": BUSY_TEXT}
    except Exception:
        yield {"event": "error", "message": "回答失败，请稍后再试"}
```

**为什么**：

- try 在 with 外面，不在里面：CircuitOpen 从 chat_stream 抛出来，先穿过 with，tracked_run 的 except 把 run 记成 failed，再到这里变成 error 事件。记账和给读者反馈是两件事，各在各的层。
- 原来 with 里的 `except GeneratorExit` 不动，它还在里面。
- 两个 except 文案不同：熔断是"休息一下"，暗示稍等就好；别的错是"失败"。Go 侧收到 error 事件会退读者额度。
- 为什么不在入口先查 `llm_breaker.state == "open"` 省掉建 run：线上版这么做是因为它入口要先检索，检索也花钱。你没有检索，chat_stream 的 before() 就是第一道门，多一条 failed 的 run 反而是证据。

**main.py**：不用改。worker 的 except Exception 会接住 CircuitOpen，回调 failed，error 里是 "llm circuit open"。

### 9.5 卡住回收：reap_stale 和 lifespan

**做什么**：runs.py 追加 `reap_stale`，main.py 用 lifespan 起一个每 5 分钟跑一次的协程。

**runs.py**：

```python
STALE_AFTER_MIN = 30


def reap_stale(max_age_min: int = STALE_AFTER_MIN) -> list[int]:
    """把卡在 running 超过 max_age_min 分钟的 run 标成 failed，返回收掉的 id。"""
    err = f"stale: 超过 {max_age_min} 分钟没有结束，进程可能中途退出"
    with connect() as conn:
        rows = conn.execute(
            """UPDATE runs SET status='failed', error=?, finished_at=datetime('now')
               WHERE status='running' AND created_at < datetime('now', ?)
               RETURNING id""",
            (err, f"-{max_age_min} minutes"),
        ).fetchall()
        return [r["id"] for r in rows]
```

**main.py**：

```python
import asyncio
from contextlib import asynccontextmanager
from runs import reap_stale

REAP_EVERY = 300   # 秒


async def reaper() -> None:
    while True:
        try:
            ids = await asyncio.to_thread(reap_stale)
            if ids:
                log.warning("runs.reaped", extra={"run_ids": ids})
        except Exception:
            log.exception("runs.reap_failed")
        await asyncio.sleep(REAP_EVERY)


@asynccontextmanager
async def lifespan(_: FastAPI):
    task = asyncio.create_task(reaper())
    yield
    task.cancel()


app = FastAPI(title="agent-runtime", lifespan=lifespan)
```

**为什么**：

- `lifespan` 是 FastAPI 的"启动时做什么、关闭时做什么"，形状和第 5 章 tracked_run 一样：yield 前是启动，yield 后是关闭。只是 async 版。
- `asyncio.to_thread(reap_stale)`：reap_stale 是同步的 SQLite 操作，放线程里跑，不堵事件循环。和第 8 章 iterate_in_threadpool 同一个理由。
- reaper 里的 try 包住整个循环体：回收失败（比如数据库锁住）记日志继续，不能让这个协程死掉，死了就再也不回收。
- `UPDATE ... WHERE status='running'` 天然幂等：多个实例同时跑也没关系，谁先改谁算。
- `RETURNING id`：SQLite 3.35 起支持，改了哪些行一次拿到，不用先查再改。
- 为什么放服务进程里不另起定时任务：少部署一个东西。多实例时重复跑无害。

**验证**：先直接调一次，看它收掉哪些：

```bash

print(reap_stale())
"
sqlite3 runs.db "select id, status, error from runs where error like 'stale%';"
```

返回被收掉的 id 列表（可能为空），查表它们都是 failed，error 以 stale 开头。然后插一条一小时前的假 running，`REAP_EVERY` 临时改成 10，重启服务，10 秒内看到 `runs.reaped` 日志：

### 自检

1. 熔断和重试是什么关系？
   答：偶发错误重试，持续错误熔断。重试在熔断之内：熔断器包在最外层，里面重试几次都失败才算熔断器的一次失败。两个都没有，厂商抖一下每个读者都等满超时。
2. 流式为什么"拿到第一片就算成功"？
   答：第一片到了说明连上了、厂商在吐字，依赖是好的。之后读者断开是读者的事，流中途出错是单次请求的事，都不该让熔断器记一笔把别的读者挡在外面。
3. 30 分钟怎么定的？以后有一个正常跑一小时的 Agent 怎么办？
   答：最长正常执行几分钟，留十倍余量。有长任务就像 线上版排除裁判那样按 agent 名排除，或者 reap_stale 按 agent 给不同阈值。
4. 为什么 _state 不存一个变量，而是每次从 _opened_at 算？
   答：少一个要同步的状态。存变量就要有人在冷却到期那一刻把 open 改成 half_open，没人做这件事；算出来的永远是对的。
5. 熔断器为什么是进程内单例而不是放数据库？
   答：它的作用是"别再发请求"，查一次数据库的代价和发一次请求差不多，就失去意义了。多进程各自计数，每个进程多失败几次才熔断，可以接受。要全局一致放 Redis，不在这章。

## 第 10 章 收口：换上 LangChain，对照 线上版

### 这一章解决什么问题

九章下来你有一个完整的运行时，底层是 httpx 手拼的请求。这章做一件事：把最底下那层换成 LangChain，上层一行不动，用三组现成的验证（pytest、出题脚本、问答 curl）证明边界是真的。做完两个版本都留着，一行 import 切换。

不做的事要先说清：**不换循环**。不用 AgentExecutor，不用 create_agent。run_loop、tracked_run、invoke_structured、Breaker、main.py 全部原样。LangChain 在这章只是模型客户端。

学完这章，再去读 线上版的 app/runtime.py 和各个 Agent，你会发现它每个 API 都对应你手写的几行，没有魔法。这是五个 Agent 教程的前提。

### 先看懂做法

**换层的办法是写适配器，不是改上层**。你的上层认的是 OpenAI 格式的字典：消息是 `{"role": ..., "content": ...}`，响应是 `data["choices"][0]["message"]`，用量是 `data["usage"]["prompt_tokens"]`。LangChain 认的是对象：`HumanMessage`、`AIMessage`、`ToolMessage`，响应是 `AIMessage`，用量在 `usage_metadata`。

两条路：改上层去认对象，或者写一个 `llm_lc.py`，对外签名和 llm.py 一模一样，里面把字典翻译成对象发出去、把对象翻译回字典交回来。走第二条。理由是第 7 章说过的判断标准：换掉一层，另一层不用知道。线上版走的是第一条，所以它的 runtime.py 里到处是 `resp.tool_calls`、`m.model_dump()`，换客户端就得改循环。这是你比它做得好的一处，笔记里记下。

**对应表**，手写的每样东西在 LangChain 里叫什么：

| 你手写的 | LangChain | 在哪 |
|---|---|---|
| `client.post("/chat/completions", json=body)` | `model.invoke(messages)` | ChatOpenAI |
| `body["tools"] = [...]`，`body["tool_choice"]` | `model.bind_tools(tools, tool_choice=name)` | 返回一个绑定了工具的新模型 |
| `data["choices"][0]["message"]["tool_calls"]`，里面 arguments 是 JSON 字符串 | `resp.tool_calls`，args 已经是字典 | AIMessage |
| arguments 不是合法 JSON | `resp.invalid_tool_calls`，args 是原始字符串 | AIMessage |
| `data["usage"]["prompt_tokens"]` | `resp.usage_metadata["input_tokens"]` | 键名变了 |
| `"stream": True` 逐行解析 `data:` | `model.stream(messages)` 逐片 AIMessageChunk | 最后一片带 usage_metadata，要 `stream_usage=True` |
| 第 2 章手写 JSON Schema | `@tool` 装饰器从函数签名生成 | 这章不用，五个 Agent 教程用 |
| 第 6 章 invoke_structured | `with_structured_output(schema, method="function_calling", include_raw=True)` | 这章不用，你的打回重试比它细 |

最后两行是这章刻意不用的：你的 pydantic_to_tool 和 invoke_structured 已经做了同样的事，而且打回时把全部错误列全送回模型，`with_structured_output` 做不到。线上版的 quiz 和 graph 后来也从 with_structured_output 退回了自己的重试，原因一样。

**max_retries 和熔断器的关系**。ChatOpenAI 自带重试，默认 2 次。第 9 章自检第 1 题说过：重试在熔断之内。这章把 `max_retries=0`，重试的事以后想加再加，先让熔断器的计数和你第 9 章验证的行为一致。

### 10.1 llm_lc.py：get_model 和两个方向的翻译

**做什么**：新建 `llm_lc.py`，三部分：按 .env 建模型、字典到对象、对象到字典。

**骨架**：

```python
# llm_lc.py
"""LangChain 版模型客户端。对外签名和 llm.py 一模一样，上层不知道底下换了。"""
import json
import os
from typing import Iterator

from dotenv import load_dotenv
from langchain_core.messages import AIMessage, HumanMessage, SystemMessage, ToolMessage
from langchain_openai import ChatOpenAI

from breaker import llm_breaker

load_dotenv()

MODEL = os.environ["LLM_MODEL"]
LLM_TIMEOUT = float(os.environ.get("LLM_TIMEOUT", 60))
TUTOR_TIMEOUT = float(os.environ.get("TUTOR_TIMEOUT", 20))


def get_model(**kwargs) -> ChatOpenAI:
    """按 .env 配置返回模型对象。换厂商只改 .env。调用方传的同名参数优先。"""
    opts = {"timeout": LLM_TIMEOUT, "max_retries": 0, "stream_usage": True, **kwargs}
    return ChatOpenAI(base_url=os.environ["LLM_BASE_URL"], api_key=os.environ["LLM_API_KEY"],
                      model=MODEL, **opts)


_model = get_model()
_tutor_model = get_model(timeout=TUTOR_TIMEOUT)


def to_lc(messages: list[dict]) -> list:
    """OpenAI 格式的字典 → LangChain 消息对象。四种 role 四个类。"""
    out = []
    for m in messages:
        role = m["role"]
        if role == "system":
            out.append(SystemMessage(m["content"]))
        elif role == "user":
            out.append(HumanMessage(m["content"]))
        elif role == "assistant":
            calls = [{"name": c["function"]["name"],
                      "args": json.loads(c["function"]["arguments"]),
                      "id": c["id"]} for c in m.get("tool_calls") or []]
            out.append(AIMessage(content=m.get("content") or "", tool_calls=calls))
        elif role == "tool":
            out.append(ToolMessage(content=m["content"], tool_call_id=m["tool_call_id"]))
        else:
            raise ValueError(f"未知 role: {role}")
    return out


def from_lc(resp: AIMessage) -> dict:
    """LangChain 的 AIMessage → 上层认的 OpenAI 格式响应字典。"""
    calls = [{"id": c["id"], "type": "function",
              "function": {"name": c["name"], "arguments": json.dumps(c["args"], ensure_ascii=False)}}
             for c in resp.tool_calls]
    calls += [...]                                         # invalid_tool_calls 也要进来，arguments 用它原始的 args 字符串
    msg = {"role": "assistant", "content": resp.content or None}
    if calls:
        msg["tool_calls"] = calls
    u = resp.usage_metadata or {}
    return {"choices": [{"message": msg}],
            "usage": {"prompt_tokens": u.get("input_tokens", 0), "completion_tokens": u.get("output_tokens", 0)}}
```

**为什么**：

- `to_lc` 里 assistant 的 tool_calls 要 `json.loads`：你的字典里 arguments 是 JSON 字符串（第 2 章的协议），LangChain 的 AIMessage 要的是已解析的字典。来回翻译就是这章的全部工作量。
- `from_lc` 里 `invalid_tool_calls` 不能漏：模型吐了不合法 JSON 时，LangChain 不抛，把它放进 `invalid_tool_calls`，args 是原始字符串。你的 invoke_structured 靠 `json.loads` 抛 JSONDecodeError 走打回分支，所以要把它原样放回 arguments。漏了这一步，不合法 JSON 的回复在上层看起来像"没有调用工具"，走错分支。
- `content or None`：LangChain 空内容是 `""`，OpenAI 原生是 `null`。上层没依赖这个，但翻译要忠实。
- 两个模型实例：问答超时 20 秒，其他 60 秒。ChatOpenAI 的 timeout 在构造时定，所以建两个，而不是每次请求传。
- `max_retries=0` 见"先看懂做法"。

**验证**：

```bash

msgs = to_lc([{'role': 'user', 'content': '用一句话介绍 RAG'}])
print(msgs)
resp = _model.invoke(msgs)
print(type(resp).__name__, resp.usage_metadata)
print(from_lc(resp))
"
```

第一行是 `[HumanMessage(...)]`，第二行 `AIMessage {'input_tokens': ..., 'output_tokens': ..., ...}`，第三行是你熟悉的 choices 加 usage 字典。

### 10.2 chat 和 chat_stream

**做什么**：llm_lc.py 追加和 llm.py 同签名的两个函数。

**骨架**：

```python
def chat(messages: list[dict], tools: list[dict] | None = None, tool_choice: dict | None = None) -> dict:
    """和 llm.chat 同签名。tools 是 OpenAI 格式的工具描述，bind_tools 直接认。"""
    model = _model
    if tools:
        choice = tool_choice["function"]["name"] if tool_choice else None
        model = model.bind_tools(tools, tool_choice=choice)
    return llm_breaker.call(lambda: from_lc(model.invoke(to_lc(messages))))


def _chat_stream_raw(messages: list[dict]) -> Iterator[dict]:
    for chunk in _tutor_model.stream(to_lc(messages)):
        if chunk.usage_metadata:
            u = chunk.usage_metadata
            yield {"text": "", "usage": {"prompt_tokens": u.get("input_tokens", 0),
                                         "completion_tokens": u.get("output_tokens", 0)}}
            continue
        if chunk.content:
            yield {"text": chunk.content}


def chat_stream(messages: list[dict], *, timeout: float = TUTOR_TIMEOUT) -> Iterator[dict]:
    yield from llm_breaker.stream(_chat_stream_raw(messages))
```

**为什么**：

- `bind_tools` 返回新对象不改原来的，所以每次要工具都重新 bind。`tool_choice` 传工具名字符串，LangChain 自己拼成 `{"type": "function", "function": {"name": ...}}`，就是你第 6 章手拼的那个。
- `pydantic_to_tool` 生成的字典 bind_tools 直接认，不用改。它内部能认 OpenAI 格式的工具字典、pydantic 类、`@tool` 函数三种，你用的是第一种。
- `timeout` 参数在 chat_stream 签名里保留但不用：`_tutor_model` 构造时已经定了 20 秒。保留是为了签名一致，调用方不用改。签名一致是适配器的全部意义。
- 熔断器照样包在外面，和 llm.py 同一个 `llm_breaker` 单例。换客户端，熔断计数不变。

**验证**：三组现成的验证全跑一遍，但先不切 import，直接调 llm_lc：

```bash
         tool_choice={'type': 'function', 'function': {'name': 'Quiz'}})
```

### 10.4 对照线上版：七项结论

教程版本写到这里，和作者的线上版放在一起对照，七项。线上版的代码你看不到，结论直接给，重点看"为什么"那一栏，每一条都对应前面某一章的决定。

| 项 | 线上版 | 教程版 | 结论 |
|---|---|---|---|
| run_loop 两个出口和工具出错 | 两个出口一样；多接一种 HTTPStatusError 把状态码给模型；循环直接认 LangChain 对象 | 认 OpenAI 字典，客户端可换 | 出口和兜错一样；分层教程版对，线上版的循环和框架绑死，换客户端要改循环 |
| runs 表字段 | 多 tenant_id、user_id、session_id、prompt_version 四列 | 没有租户和提示词版本 | 线上版对，这四列是多租户和评测的前提，五个 Agent 教程会补 |
| tracked_run | 有，但没有任何 Agent 在用，start_run / finish_run 直接调的地方 8 个文件 33 处 | 第 5 章起全部走 tracked_run | 教程版对；写了基座不用，等于没写 |
| 结构化输出重试 | 四个 Agent 各自一个 for attempt 循环，都用 with_structured_output，四份 | 一个 invoke_structured，Agent 只给 schema 和 check | 教程版对，四份逻辑相同，改一处漏三处 |
| worker | 五份逐行相同，而且是"跑 Agent 和回调 done 放一个 try"的形状，回调失败会被记成 Agent 失败 | 一个 job_worker，两个 try | 教程版对，这是第 7 章亲手跑出来的 bug，线上版五处都有 |
| breaker 流式判定 | 完全一样；问答入口多一个 `state == "open"` 预检，因为它先要检索，检索也花钱 | 没有预检 | 一样；预检在有检索时才需要 |
| reap_stale | 排除评测裁判，用 PostgreSQL 的 make_interval | 不排除，SQLite 的 datetime 偏移 | 线上版对，裁判一批跑几十分钟不能收；教程版现在没有裁判 |

读这张表的方法：线上版先写、教程版后写，后写的在分层上更干净，先写的在业务字段上更全。两边都对的地方说明那个决定是稳的，比如熔断器的流式判定。

### 自检

1. 换了客户端上层为什么能不动？
   答：上层只认 OpenAI 格式的字典，llm_lc 在边界上双向翻译。上层不知道底下是 httpx 还是 LangChain。
2. 线上版的 run_loop 为什么换客户端就得改？
   答：它直接认 LangChain 对象，`resp.tool_calls`、`ToolMessage(...)` 写在循环里。它选了"上层认对象"那条路，少一层翻译，代价是和框架绑死。
3. invalid_tool_calls 为什么必须翻译回去？
   答：你的 invoke_structured 靠 json.loads 抛错来识别"参数不是合法 JSON"。LangChain 把它单独放了，不翻译回去上层以为模型没调工具，走错分支。
4. 为什么不用 with_structured_output？
   答：你的打回重试把全部错误列全送回模型，并记每次尝试的坏样本进 steps 表；它只给 parsed 和 raw，重试要自己写，写出来就是你已有的那份。
5. max_retries 为什么设 0？
   答：让熔断器的失败计数和第 9 章验证的行为一致。重试在熔断之内，要加也是在熔断器包着的那层里加，而且加了要重新想 fail_max 的含义。
